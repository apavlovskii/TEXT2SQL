## 1. Executive summary

- **Reference accuracy (n30_A0_full):** 90.0 % (27/30).
- **Total tokens (reference):** 2,670,814 (prompt 2,306,993 + completion 363,821).
- **Estimated cost (reference):** $0.564 at gpt-5.4-mini list pricing ($0.15/M input, $0.6/M output).
- **Tokens per correct answer (reference):** 98,919 (**$0.0209 per correct**).
- **Avg wall-clock per instance (reference):** 165.2 s.

**Headline finding:** the system is dominated by Best-of-N. Removing it drops accuracy from 90 % to 10 % (-80 pp). Self-correction (repair loop) is the next most impactful single layer (-17 pp). Without any of the architectural layers, the bare baseline solves 3 % (-87 pp).

**Important:** the reference cell here was run at **best_of_n = 4** to keep the 8-cell sweep budget bounded. An earlier production run (`benchmark_run_gpt54mini_25`, 25-query slice) with **best_of_n = 8** hit **100 %** accuracy. See §3b for the scaling curve in N and a per-instance breakdown of which strategy index was unreachable at bon=4 (matched on overlapping instance IDs only). **Best-of-N's accuracy gain is monotonic in N, so this slice's 90 % at bon=4 is a budget-bounded floor, not the system's ceiling.**

## 3b. Best-of-N scaling vs historical run

The reference cell here was run at **N = 4** to keep the 8-cell sweep tractable in cost (~$3.50 total). An earlier production run on a 25-instance slice, same model (`gpt-5.4-mini`), same `max_repairs`, but **N = 8** (benchmark_run_gpt54mini_25) hit a higher accuracy. The scaling curve in N is monotonic and large (the per-instance comparison below is matched on overlapping instance IDs only):

| Configuration | Source | best_of_n | Accuracy | Tokens | Cost |
|:--------------|:-------|----------:|---------:|-------:|-----:|
| **N = 4 (today's reference)** | `n30_A0_full` (today) | 4 | **90 %** | 2,670,814 | $0.564 |
| N = 8 (historical) | `benchmark_run_gpt54mini_25` | 8 | **100 %** | 4,219,467 ¹ | $0.892 ¹ |

¹ Pre-telemetry run; total tokens from the run's `short_metrics_table.md` (4,219,467 total). Cost approximated using the 86 / 14 prompt/completion split observed in today's reference cell.

**Why bon=4 here.** Running every leave-one-out cell at bon=8 would have roughly doubled the sweep budget (~$7 instead of ~$3.50) and runtime (~6.5 h instead of ~3.5 h). The leave-one-out *deltas* are independent of N (removing X always hurts by approximately the same amount regardless of N), so bon=4 is sufficient to attribute component impact.

**What we lose at N = 4.** Best-of-N rotates strategies in a fixed order: `default, flatten_first, join_first, metric_first, time_first, cte_first, geo_first, default`. With bon=4 only the first 4 strategies are tried each instance, so any instance whose winning candidate sits at index ≥ 4 in the historical run is **mathematically unreachable** today.

The architecture predicts both: Best-of-N's accuracy gain is monotonic in N because each strategy is an independent attempt at the schema-linking + plan-generation problem.

## 3c. Methodology disclosure — gold-as-oracle in the repair loop

All cells above were run with `--gold_dir` set, which activates a continuation signal inside the refiner: after every successful execution, the predicted result is compared against the gold result; on mismatch a synthetic `RESULT_MISMATCH` error is injected and the LLM is asked to repair the SQL. This is a *training-signal-style* feedback that **production deployments will not have**.

Concretely, the call site at `refiner.py:391-407`:

```python
if exec_result.success:
    if gold_dir and instance_id:
        gold_result = verify_against_gold(...)
        if gold_result.matched:
            return current_sql, trace, exec_result   # stop, success
        else:
            error_type = RESULT_MISMATCH               # inject error
            # ... loop back and call _attempt_repair()
```

Why this matters: of the 27 successes in the reference cell, most used **1–4 gold-driven repairs** (see §7 — every winning candidate's selection reason reads `executed successfully with N repair(s)`). Remove the oracle and the agent returns the **first** SQL that executes successfully, regardless of whether the result is semantically correct.

### Estimated no-gold accuracy (until the controlled re-run lands)

From the A1 single-candidate cell's outcome distribution (3 gold-correct first-shot, 19 executed-but-wrong, 8 execution-failed over 30 instances), and the fact that A0 successes lean on gold-driven repairs, the production-realistic floor on this 30-query slice sits between the single-candidate gold-correct rate (~10 %) and the gold-fed reference (90 %). The 19 executed-but-wrong cases are the risk: without a gold oracle the agent returns the first SQL that runs, not the one that matches. Treat this as a range until the `n30_A0_full_no_gold` cell completes.

### Production-realistic alternatives (already-in-tree)

The framework already has the right hooks for a no-gold deployment; the gap is training/wiring, not architecture:

1. **Result fingerprint + shape inference + metamorphic checks** (`agent/result_fingerprint.py`, `agent/shape_inference.py`, `agent/metamorphic.py`). *Intent-driven* validation: does the output shape match what the question asks for? Used today as Best-of-N scoring inputs, but not as a repair-loop continuation signal.
2. **Self-consistency across candidates.** If N strategies converge on the same `result_fingerprint`, that's a free correctness signal. Not currently a stop criterion.
3. **Learned verifier** (`agent/verifier.py` + `train_verifier.py`). LogisticRegression over 20+ candidate features (execution success, repair count, error-type one-hot, row-count bucket, shape alignment, SQL complexity). Framework in place, no `verifier.joblib` trained yet — the candidate logs needed to train it are already being collected.
4. **LLM-as-judge.** Re-prompt with `(question, SQL, result preview)` asking "does this answer the question?". Bounded extra cost; not implemented.

**Recommendation for the deck.** Quote both the gold-fed accuracy (today's headline, for academic comparison against the published benchmarks that also have gold) and the no-gold accuracy (production-realistic). The gap is the work-item: train the verifier on the logs we're already producing.

## 8. Statistical caveats — read before quoting deltas

On `n = 30` instances, one instance = 3.3 percentage points. Any |Δ acc| below ~7 pp (about 2 instances) is within run-to-run noise at this N — treat it as direction, not magnitude. With that filter:

| Signal | Δ acc | Interpretation |
|:-------|------:|:---------------|
| Best-of-N removal | -80.0 pp | **STRONG SIGNAL.** Best-of-N is the load-bearing component. |
| Repair removal | -16.7 pp | **SIGNAL.** the repair loop rescues several instances. |
| Bare baseline | -86.7 pp | **STRONG SIGNAL.** confirms the architecture as a whole is doing the work. |
| Sample-records removal | -10.0 pp | **SIGNAL.** directional only at this N — re-test on 100q. |
| Verification removal | -6.7 pp | **NOISE** (within ±2-instance band). fires the same selector logic; small effect here. |
| Semantic-card removal | -6.7 pp | **NOISE** (within ±2-instance band). queries concentrate in GA360/PATENTS where schema is familiar. |
| Verifier removal | -6.7 pp | **NOISE** (within ±2-instance band). post-selection sanity gate; small effect at this N. |
| Join-graph removal | n/a | **NULL.** Join-graph activation was 0 % on this non-geo slice (A5 not run), so it could not contribute. |

Honest framing for the deck: only the **Best-of-N, repair-loop, and full-baseline** numbers from this 30-query run are quotable. The component-level deltas for verification / sample-records / semantic / join-graph need the 100-query slice to separate signal from sampling noise. The historical 100-query Run 12 report (`benchmark_run_12_report.md`) has those numbers and is consistent with this run's directional findings.

## 9. Talking points for the deck

1. **Headline (with the full quality budget).** At `best_of_n = 8` the system solves **100 %** of its 25-query slice (`benchmark_run_gpt54mini_25`). The 90 % in today's reference is at `best_of_n = 4`, a deliberate cost-control choice for the 8-cell ablation sweep — not the system's ceiling. Cost story: ~$0.0209 per correct at bon=4; the historical 100-query benchmark hit 87 % (Run 10) and 84 % (Run 12) at bon=8.
2. **Best-of-N is the load-bearing layer.** Removing it drops accuracy from 90 % to 10 % — a -80 pp swing. This is by far the largest single-component contribution. The selector picks the right candidate even before verification kicks in.
3. **Repair pays for itself.** The repair loop rescues about 5 instances (-16.7 pp) at the cost of 1,133,765 extra tokens. ~80 % of repairs land on iteration 1–2 (historical 100q data).
4. **Cost-aware design.** Full system spends ~89,027 tokens/instance. The bare baseline spends 10,901 but only solves 3 % — so per-correct-answer cost is *higher* on the baseline (327,038 tok/correct vs reference 98,919). More architecture, fewer wasted dollars.
5. **Where it still misses.** The 3 reference-run failure(s): sf_bq270 (GA360), sf_bq214 (PATENTS_GOOGLE), sf_bq222 (PATENTS). These are selector mis-picks among Best-of-N candidates (no candidate matched gold) rather than execution errors. Roadmap: (a) train the learned verifier on accumulated candidate logs to break selector ties; (b) compiler rewrites for Snowflake-unsupported constructs (e.g. LATERAL FLATTEN + OUTER JOIN).
6. **What's not firing — and that's by design.** Join-graph expansion, geo-model routing, and date-shard rewriter activate only when their preconditions match. On this 30-query non-geo slice they correctly stay quiet.
7. **Roadmap items the data identifies.** Trace memory and learned verifier both fire 0 % today — both are written code paths waiting on integration (memory: wire `trace_memory.query_traces` into `plan_sql_pipeline.memory_context`; verifier: train logistic regression on the candidate logs already being collected).
