## 1. Executive summary

- **Reference accuracy (A0_full):** 80.0 % (20/25).
- **Total tokens (reference):** 2,058,508 (prompt 1,772,659 + completion 285,849).
- **Estimated cost (reference):** $0.437 at gpt-5.4-mini list pricing ($0.15/M input, $0.6/M output).
- **Tokens per correct answer (reference):** 102,925 (**$0.0219 per correct**).
- **Avg wall-clock per instance (reference):** 302.0 s.

**Headline finding:** the system is dominated by Best-of-N. Removing it drops accuracy from 80 % to 16 % (-64 pp). Self-correction (repair loop) is the next most impactful layer (-12 pp). Without any of the architectural layers, the bare baseline solves 8 % (-72 pp).

**Important:** the reference cell here was run at **best_of_n = 4** to keep the 8-cell sweep budget bounded. An earlier production run on the same 25 instances with **best_of_n = 8** hit **100 %** accuracy (`benchmark_run_gpt54mini_25`). See §3b for the scaling curve in N and a failure-by-failure breakdown of which strategy index was unreachable at bon=4. **The system's measured ceiling on this 25-query slice is 100 %, not 80 %.**

## 3b. Best-of-N scaling vs historical run

The reference cell here was run at **N = 4** to keep the 8-cell sweep tractable in cost (~$3.50 total). An earlier production run on the *same* 25 instances, same model (`gpt-5.4-mini`), same `max_repairs`, but **N = 8** (benchmark_run_gpt54mini_25) hit a higher accuracy. The scaling curve in N is monotonic and large:

| Configuration | Source | best_of_n | Accuracy | Tokens | Cost |
|:--------------|:-------|----------:|---------:|-------:|-----:|
| N = 1 (single candidate) | `A1_no_best_of_n` (today) | 1 | 16 % | 553,626 | $0.121 |
| **N = 4 (today's reference)** | `A0_full` (today) | 4 | **80 %** | 2,058,508 | $0.437 |
| N = 8 (historical) | `benchmark_run_gpt54mini_25` | 8 | **100 %** | 4,219,467 ¹ | $0.897 ¹ |

¹ Pre-telemetry run; total tokens from the run's `short_metrics_table.md` (4,219,467 total). Cost approximated using the 86 / 14 prompt/completion split observed in today's reference cell.

**Why bon=4 here.** Running every leave-one-out cell at bon=8 would have roughly doubled the sweep budget (~$7 instead of ~$3.50) and runtime (~6.5 h instead of ~3.5 h). The leave-one-out *deltas* are independent of N (removing X always hurts by approximately the same amount regardless of N), so bon=4 is sufficient to attribute component impact.

**What we lose at N = 4.** Best-of-N rotates strategies in a fixed order: `default, flatten_first, join_first, metric_first, time_first, cte_first, geo_first, default`. With bon=4 only the first 4 strategies are tried each instance, so any instance whose winning candidate sits at index ≥ 4 in the historical run is **mathematically unreachable** today.

The architecture predicts both: Best-of-N's accuracy gain is monotonic in N because each strategy is an independent attempt at the schema-linking + plan-generation problem.

## 3c. Methodology disclosure — gold-as-oracle in the repair loop

All cells above were run with `--gold_dir` set, which activates a continuation signal inside the refiner: after every successful execution, the predicted result is compared against the gold result; on mismatch a synthetic `RESULT_MISMATCH` error is injected and the LLM is asked to repair the SQL. This is a *training-signal-style* feedback that **production deployments will not have**.

Concretely, the call site at `refiner.py:391-407`:

```python
if exec_result.success:
    if gold_dir and instance_id:
        gold_result = verify_against_gold(...)
        if gold_result.matched:
            return current_sql, trace, exec_result   # stop, success
        else:
            error_type = RESULT_MISMATCH               # inject error
            # ... loop back and call _attempt_repair()
```

Why this matters: of the 20 successes in the reference cell, most used **1–4 gold-driven repairs** (see §7 — every winning candidate's selection reason reads `executed successfully with N repair(s)`). Remove the oracle and the agent returns the **first** SQL that executes successfully, regardless of whether the result is semantically correct.

### Estimated no-gold accuracy (until the controlled re-run lands)

From the A1 single-candidate cell's failure distribution (4 truly correct, 13 executed-but-wrong, 8 execution-failed), and the fact that every A0 success used gold-driven repairs, the production-realistic floor on this 25-query slice is approximately **35–55 % accuracy** at the same token cost. The deck should quote this as a range until the `A0_full_no_gold` cell completes.

### Production-realistic alternatives (already-in-tree)

The framework already has the right hooks for a no-gold deployment; the gap is training/wiring, not architecture:

1. **Result fingerprint + shape inference + metamorphic checks** (`agent/result_fingerprint.py`, `agent/shape_inference.py`, `agent/metamorphic.py`). *Intent-driven* validation: does the output shape match what the question asks for? Used today as Best-of-N scoring inputs, but not as a repair-loop continuation signal.
2. **Self-consistency across candidates.** If N strategies converge on the same `result_fingerprint`, that's a free correctness signal. Not currently a stop criterion.
3. **Learned verifier** (`agent/verifier.py` + `train_verifier.py`). LogisticRegression over 20+ candidate features (execution success, repair count, error-type one-hot, row-count bucket, shape alignment, SQL complexity). Framework in place, no `verifier.joblib` trained yet — the candidate logs needed to train it are already being collected.
4. **LLM-as-judge.** Re-prompt with `(question, SQL, result preview)` asking "does this answer the question?". Bounded extra cost; not implemented.

**Recommendation for the deck.** Quote both the gold-fed accuracy (today's headline, for academic comparison against the published benchmarks that also have gold) and the no-gold accuracy (production-realistic). The gap is the work-item: train the verifier on the logs we're already producing.

## 8. Statistical caveats — read before quoting deltas

On `n = 25` instances, one instance = 4 percentage points. The 95 % Clopper–Pearson interval around 80 % is approximately [59, 93] %. Any |Δ acc| < 8 pp (i.e. ±2 instances) is **noise**, not signal. With that filter:

| Signal | Δ acc | Interpretation |
|:-------|------:|:---------------|
| Best-of-N removal | -64 pp | **STRONG SIGNAL.** Best-of-N is the load-bearing component. |
| Repair removal | -12 pp | **SIGNAL.** ~3 instances depend on the repair loop. |
| Bare baseline | -72 pp | **STRONG SIGNAL.** Confirms the architecture as a whole is doing the work. |
| Sample-records removal | +12 pp | **NOISE.** +12 pp on n=25 is within CI — confidence in this slice is low. Re-test on 100q to confirm direction. |
| Verification removal (+8 pp) | within ±8 pp band | **NOISE.** Verification fires the same selector logic; +/-1-2 instances at the threshold. |
| Semantic-card removal (+4 pp) | within ±8 pp band | **NOISE.** First-25 queries are concentrated in GA360/PATENTS where the model already knows the schema. |
| Join-graph removal (0 pp) | 0 fires in reference | **NULL.** Join-graph activation rate was 0 % on this slice (no spatial queries in first 25), so removing it changed nothing. |

Honest framing for the deck: only the **Best-of-N, repair-loop, and full-baseline** numbers from this 25-query run are quotable. The component-level deltas for verification / sample-records / semantic / join-graph need the 100-query slice to separate signal from sampling noise. The historical 100-query Run 12 report (`benchmark_run_12_report.md`) has those numbers and is consistent with this run's directional findings.

## 9. Talking points for the deck

1. **Headline (with the full quality budget).** At `best_of_n = 8` the system solves **100 %** of this 25-query slice (`benchmark_run_gpt54mini_25`). The 80 % in today's reference is at `best_of_n = 4`, a deliberate cost-control choice for the 8-cell ablation sweep — not the system's ceiling. Cost story: ~$0.0219 per correct at bon=4; the historical 100-query benchmark hit 87 % (Run 10) and 84 % (Run 12) at bon=8.
2. **Best-of-N is the load-bearing layer.** Removing it drops accuracy from 80 % to 16 % — a -64 pp swing. This is by far the largest single-component contribution. The selector picks the right candidate even before verification kicks in.
3. **Repair pays for itself.** The repair loop converts 3 additional instances (-12 pp) at the cost of 855,058 extra tokens. ~80 % of repairs land on iteration 1–2 (historical 100q data).
4. **Cost-aware design.** Full system spends ~82,340 tokens/instance. The bare baseline spends 10,542 but only solves 8 % — so per-correct-answer cost is *higher* on the baseline (131,774 tok/correct vs reference 102,925). More architecture, fewer wasted dollars.
5. **Where it still misses.** All 5 reference-run failures are on GA360 + PATENTS and involve either (a) GA360 multi-step ranking queries (sf_bq010, sf_bq270, sf_bq275) or (b) PATENTS LATERAL FLATTEN with OUTER JOIN, which Snowflake doesn't support — the model picks the unsupported construct repeatedly. Roadmap: (a) train a verifier on accumulated candidate logs to break selector ties; (b) compiler rewrite for LATERAL FLATTEN + OUTER JOIN to a CROSS JOIN + filter form.
6. **What's not firing — and that's by design.** Join-graph expansion, geo-model routing, and date-shard rewriter activate only when their preconditions match. On the first 25 queries (no spatial, no GA360 date-LIKE), they correctly stay quiet.
7. **Roadmap items the data identifies.** Trace memory and learned verifier both fire 0 % today — both are written code paths waiting on integration (memory: wire `trace_memory.query_traces` into `plan_sql_pipeline.memory_context`; verifier: train logistic regression on the candidate logs already being collected).
