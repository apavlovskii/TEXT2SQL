## Slide 3 — Architecture in one frame

Five layers, each justified by a published idea:

1. **Hybrid retrieval** (BM25 + `text-embedding-3-large`, RRF k=60) — Cormack et al., 2009.
2. **Entity-oriented index** — `TableCard`, `ColumnCard`, `JoinCard`, `SemanticCard`, `SampleRecord`, `TraceMemory`, `SnowflakeSyntax`. Each card is one discrete metadata element. ~622 + 5 762 + … items in ChromaDB.
3. **Plan → SQL compiler** (deterministic) — separates LLM reasoning from SQL formatting; closes a whole class of `LATERAL FLATTEN` / quoting errors.
4. **Best-of-N with strategy diversification + multi-signal selector** — Wang et al. (Self-Consistency) generalized to *structurally* diverse prompts (`join_first`, `metric_first`, `time_first`, `flatten_first`, `cte_first`, `geo_first`).
5. **Self-correction loop** with category-classified errors — Madaan et al. (Self-Refine) specialized to 8 Snowflake error categories.

Speaker note: each layer maps to an academic primitive. The contribution is **how they compose** for industrial schemas, not the primitives themselves.

## Slide 4 — What's actually new

- **First demonstration on Spider 2.0 — Snow that RAG outperforms full agentic pipelines on industrial schemas while costing 6.9× fewer tokens.**
- **Deterministic Plan → SQL compiler** as architectural separation. The LLM no longer owns SQL formatting — it owns intent.
- **Partition collapsing as an index-time step** for temporally-sharded sources (GA360, GA4): 366 daily tables → 1 representative card. Without this, GA360 retrieval is unreachable.
- **Multi-stage SchemaSlice post-processing** — protected identifiers (joins, time columns resist trimming), 1-hop join-graph expansion, VARIANT enrichment.
- **Reproducibility infrastructure** — every run captures `manifest.json` with config snapshot + git hash; `instance_results.jsonl` per-question telemetry; cross-experiment comparison built-in.

## Slide 13 — APEX-SQL: Best Academic Competitor (KDD 2026)

**Paper:** *"APEX-SQL: Talking to the Data via Agentic Exploration for Text-to-SQL"* — Bowen Cao, Weibin Liao, Yushi Sun et al. (CUHK / Peking University / Tencent Lightspeed). KDD 2026. arXiv:2602.16720. Code: github.com/Tencent/APEX-SQL-Project.

**Core thesis:** Static schema representations fail to resolve semantic ambiguity in real enterprise databases (opaque column names, domain codes, value-format conventions). APEX-SQL shifts "from passive schema perception to agentic exploration" — it forms hypotheses about the data, runs exploratory SQL against the live database to verify them, and only then generates the final query.

**Two-stage architecture:**

**Stage 1 — Schema Linking (4 components)**

| Step | What it does | Key number |
|:-----|:-------------|:-----------|
| **1. Hypothesis Generation** | Generates N=2 schema-*agnostic* reasoning plans (temperature 0.8), deliberately isolating high-level intent from schema vocabulary noise. Aggregates to one master plan at temperature 0.2. | Basis for all downstream steps |
| **2. Dual-Pathway Pruning** | Two simultaneous passes over all columns: negative pass (columns to delete) + positive pass (columns to keep). A column survives unless *both* passes reject it. Compresses ~3 430 cols → ~383 cols (9× reduction, ~7 k tokens). | Full dual path: **97.5% SRR**; deletion only: 80.8%; selection only: 93.3% |
| **3. Parallel Data Profiling** | Independent agents per table run role-specific exploratory SQL queries against the live DB. Validates column semantics empirically — checks actual value formats, NULL rates, FK integrity. Results >30 rows compressed to top 10 + statistics. | Removing this step: ↓9.2% SRR |
| **4. Global Synthesis** | Integrates cross-table observations; enforces topological connectivity (all join paths must be traversable). Includes a semantic linking sub-step that hypothesizes table/column roles before profiling. | Removing all agentic verification: ↓21.7% SRR |

SRR = Strict Recall Rate on Spider 2.0-Snow (N=120 pilot). Baseline ReFoRCE schema linking: **35.0% SRR**.

**Stage 2 — SQL Generation**

*Pre-processing (run once per task before the agent loop):*
- **Macro Plan Aggregation** (`preprocess_macro_plans.py`): consolidates multiple reasoning paths into a unified master plan injected into the agent's initial context.
- **Deterministic Guidance Retrieval** (`preprocess_select_tips.py`): rule engine maps operational keywords from the plan to one of **14 directive categories** in a pre-built library ℳ (Join Strategy, Aggregation, NULL inspection, String Matching, etc.). >95% recall. Adding guidance: **+3.75–4.27% EX@8** on GPT-4o / GPT-5.

*Agentic Exploration Loop (max 40 actions, 56 k token budget; SQL synthesis force-triggered at 52 k):*

| Action | Purpose |
|:-------|:--------|
| **PROFILING** | Autonomously generates exploratory SQL — distributions, NULL checks, FK validation, value ranges |
| **CONSOLIDATION** | Periodic state compression: prunes history to exploratory queries + execution results + latest plan. Prevents context bloat. |
| **SQL SYNTHESIS** | Maps accumulated evidence to physical SQL. Re-enters loop on execution error. |
| **CONFIRMATION** | Secondary semantic verification against requirements + accumulated observations before finalizing. |

*Answer selection:*
- **8 samples** (Pass@8), majority voting on execution results.
- Reward model (`ContextualAI/ctx-bird-reward-250121`) as tie-breaker when consensus fails.
- `--revote` flag to redo selection on cached samples.

**Benchmark results:**

| Benchmark | N | Model | EX | Pass@8 |
|:----------|:--|:------|---:|-------:|
| Spider 2.0-Snow | 547 | DeepSeek-R1 | **53.03%** | **68.44%** |
| BIRD-Dev | 1 534 | GPT-4o | **70.7%** | — |
| Spider 2.0-Snow schema linking | 120 | GPT-4.1 | 88.33% SRR | — |

**Ablation highlight — exploration effect on Spider 2.0-Snow (oracle schema, N=120):**

| Model | w/ Exploration | w/o Exploration | Δ EX |
|:------|---------------:|----------------:|-----:|
| DeepSeek-V3.2 | 57.50% | 39.17% | **+18.33%** |
| GPT-4o | 41.67% | 36.67% | +5.00% |
| Kimi-k2-instruct | 48.33% | 38.33% | +10.00% |

"Rich get richer" finding: stronger models gain proportionally larger improvements from exploration.

**Primary bottleneck identified by the authors:** Pass@8 = 68.44% vs. voted EX = 53.03% — 15 pp lost to answer selection. The paper explicitly names selection as the next frontier.

Speaker note: APEX-SQL is the first published academic system to break 50% on Spider 2.0-Snow. The exploration-vs.-selection gap is directly analogous to our Best-of-N result: 80% (Best-of-N) vs. 16% (no Best-of-N) — the ceiling is in the candidates, the bottleneck is in selection.

## Slide 14 — Databricks Genie: Commercial Architecture

**Product identity:** AI/BI Genie — Databricks' conversational NL-to-SQL product, embedded in the Data Intelligence Platform. GA announced June 2025. Over 4 000 customers in preview. Architecture is disclosed through documentation and release notes; internals (model versions, retrieval mechanics) are partly opaque.

**Fundamental architectural philosophy:** Genie is the *opposite* of APEX-SQL. Rather than having the LLM explore the schema at runtime, Genie invests **up-front human curation** to narrow the LLM's task. Domain experts curate a **Genie Space**; at query time the LLM selects from verified patterns rather than reasoning over the entire schema.

**The Genie Space — configuration unit:**

| Resource | Limit | What it contains |
|:---------|:------|:-----------------|
| Tables / views | **30 hard limit** | Scoped Unity Catalog tables for this domain |
| Knowledge store snippets | **200** | Table/column descriptions, SQL expressions (KPIs, filters, row transforms), join definitions, synonyms |
| Instructions | **100** | Parameterized example SQL queries + general text rules (effective up to ~20 lines) |
| Entity matching | **120 columns**, **1 024 values each** | Pre-sampled distinct-value lists for categoricals |

**5-layer schema linking:**

1. **Unity Catalog metadata** (always active): schema, data types, PK/FK relationships, column descriptions.
2. **Intelligent filtering** (mechanism not disclosed — likely BM25/embedding): at query time, selects relevant columns and example SQL from the Space's knowledge store.
3. **Entity matching**: pre-sampled distinct-value lists for categorical columns. Resolves *"Florida"* → `WHERE state = 'FL'`; *"first level"* → exact DB code. Filters become UI dropdowns from stored values.
4. **Join relationships**: explicit definitions stored in knowledge store; auto-suggested from Unity Catalog FK metadata.
5. **Genie Ontology** (newer, workspace-wide): automatically built map of tables, dashboards, notebooks, and connected external docs (Google Drive, SharePoint via MCP). Workspace-level semantic layer distinct from per-Space stores.

**LLM backend — compound AI system (model rotation, opaque):**

| Mode | Primary model | Fallback |
|:-----|:-------------|:---------|
| Standard Genie Spaces | **Azure OpenAI** | Databricks-hosted open-weight models |
| Partner AI (opt-in) | **Anthropic Claude** (option) | — |
| Agent Mode / Research Agent | **Anthropic Claude Sonnet** (explicitly stated) | — |

Databricks is explicit: "a managed service that continuously evaluates models from multiple providers and uses the most performant and accurate options." Model versions are not disclosed and have changed at least twice (Nov 2024, Sep 2025).

**Agentic evolution — key milestones:**

| Date | Change |
|:-----|:-------|
| Feb 2025 | Chain-of-Thought reasoning added to text-to-SQL model |
| Sep 2025 | **Self-reflection**: generates SQL, checks own output before execution |
| Nov 2025 | Research Agent: single unified reasoning agent replaces multi-hypothesis parallel approach |
| Dec 2025 | Semantic ambiguity detection: asks clarifying questions before generating |
| Apr 2026 | Agent Mode publicly available (UI only — not exposed via API) |

**Research Agent loop (Agent Mode):**
Parse question → create research plan with hypotheses → execute SQL per hypothesis in parallel → reflect on each result → iterate → generate report with citations and visualizations. Uses Claude Sonnet. Scales reasoning depth to question complexity.

**Trusted Assets — the key differentiator:**
- **Parameterized example SQL**: if the user's question matches a trusted asset's NL question, Genie runs the verified SQL *directly* (parameter-substituted), skipping generation entirely. Response is flagged "Trusted."
- **SQL UDFs (Unity Catalog)**: exact function logic executes, always "Trusted."
- Effect: for frequently-asked or high-stakes queries, the LLM is completely bypassed.

**Human-in-the-loop knowledge mining:** thumbs-up on a response triggers Genie to suggest new SQL expressions and join definitions for the knowledge store. Iterative improvement without automated fine-tuning. Databricks is explicit: "we do not train foundation models on your data."

**Governance:** read-only SQL only (SELECT); per-user Unity Catalog permissions enforced at execution time; compute credentials embedded at Space creation.

**Published benchmark numbers:** none. No public Spider / BIRD comparison.

Speaker note: Genie and APEX-SQL represent opposite extremes of the design space — zero setup / runtime exploration (APEX-SQL) vs. high setup / curated retrieval (Genie). SnowRAG-Agent sits between them: moderate index-build cost once, fast query time, full-schema coverage without the 30-table ceiling.

## Slide 15 — Three-Way Architecture Comparison

| Dimension | **SnowRAG-Agent** (this work) | **APEX-SQL** (KDD 2026) | **Databricks Genie** |
|:----------|:------------------------------|:------------------------|:---------------------|
| **Design philosophy** | Dynamic RAG + deterministic compiler | Agentic hypothesis-verification | Curated RAG + trusted assets |
| **Schema scope** | Full DB via vector/BM25 index; SchemaSlice post-filtering | Full DB; agent explores at runtime | Hard limit: 30 tables per Space |
| **Schema linking** | Hybrid retrieval (BM25 + `text-embedding-3-large`, RRF k=60) + SchemaSlice | 4-stage: hypothesis → dual-path pruning → parallel profiling → global synthesis | 5-layer: UC metadata + filtering + entity matching + join defs + Ontology |
| **SQL generation** | Plan → SQL compiler (deterministic); LLM owns intent, compiler owns syntax | 4-action agentic loop; force-triggers synthesis at 52 k tokens | CoT + self-reflection; trusted assets bypass generation entirely |
| **Self-correction** | Category-classified repair loop (8 Snowflake error categories; Madaan Self-Refine) | SYNTHESIS re-enters exploration loop on execution error | Self-reflection pre-execution + human "Ask for Review" escalation |
| **Best-of-N / selection** | Best-of-N with 6 structural strategy variants; multi-signal selector | 8 samples; majority voting + reward model tie-breaker | Not disclosed; single-pass with reflection |
| **Large schema handling** | Partition collapsing (366 GA360 tables → 1 card); VARIANT enrichment; 1-hop join-graph expansion | 9× column compression at schema-linking time; 40-action budget caps runtime cost | Forces 30-table scope; multiple Spaces for large orgs; Genie Ontology for workspace-level coverage |
| **Domain adaptation** | Index rebuild on schema change (minutes for 20 Snowflake DBs) | Pre-processing runs per task (evidence linking → plans → tips); deterministic tips library ℳ curated once | High up-front: curate knowledge store, entity lists, trusted assets, example SQL |
| **Governance / safety** | None (research system) | None (research system) | Deep Unity Catalog; per-user permissions at execution time; read-only SQL enforced |
| **LLM** | Provider-neutral; today `gpt-5.4-mini` | Any OpenAI-compatible endpoint; best: DeepSeek-R1, GPT-4.1 | Compound AI — Azure OpenAI primary; Claude Sonnet for Agent Mode; rotates without disclosure |
| **Spider 2.0-Snow EX** | **87% (100q slice)** | **53.03% (547q, updated script)** | Not published |
| **BIRD EX** | Not evaluated | **70.7%** | Not published |
| **Cost / correct answer** | **$0.11** | Not reported | Not reported |
| **Open source** | This repo | github.com/Tencent/APEX-SQL-Project | Closed source |

**Why SnowRAG-Agent outperforms APEX-SQL on the queries we measured:**

1. **Deterministic compiler**: APEX-SQL's agentic loop still lets the LLM own SQL *formatting*. SnowRAG-Agent's Plan→SQL compiler closes the entire class of Snowflake-specific syntax errors (`LATERAL FLATTEN`, VARIANT access, quoting) by separating intent from syntax. APEX-SQL's 14-category directive library addresses this partially but the LLM still emits raw SQL.

2. **Partition collapsing**: APEX-SQL's runtime exploration would encounter 366 GA360 daily tables as separate entities — schema linking noise makes GA360 queries near-unreachable. SnowRAG-Agent collapses them at index time into one representative card; retrieval is deterministic.

3. **Known cost profile**: APEX-SQL runs 8 samples × up to 40 agentic actions per question. No cost figure is published. SnowRAG-Agent is measurably $0.11/correct answer (Best-of-N-6 with `gpt-5.4-mini`).

**Why Genie wins on reliability and governance (and where SnowRAG-Agent could match it):**
- Trusted assets bypass LLM generation for known queries — guaranteed correctness for high-frequency business questions. SnowRAG-Agent's `TraceMemory` card is the architectural equivalent but is not yet wired into the query path (roadmap item: Slide 10).
- Unity Catalog permissions enforced at execution time — enterprise-grade governance SnowRAG-Agent does not attempt.

**Honest comparison caveat:** SnowRAG-Agent's 87% is on a 100q subset; APEX-SQL's 53.03% is on the full 547q eval with a different (updated) evaluation script. These are not directly comparable. The correct next step is a head-to-head run on the same 547q set with the same script. Our 100q ablation numbers are internally consistent and the architecture conclusions hold; the cross-system comparison needs the same evaluation harness.
