## Аннотация

До активного внедерения в практику корпоративной аналитики моделей искусственного интеллекта работа с большими объемами промышленных данных как правило требовала привлечения ИТ специалистов со знанием языка SQL. Зачастую эксперты доменной области такими знаниями не обладали, что приводило к удорожанию и усложнению процессов обработки информации и принятия управленческих решений. В связи с этим задача автоматической трансляции запросов на естественном языке в SQL-команды приобретает высокую практическую ценность для бизнеса, поскольку позволяет снизить порог доступа к данным, ускорить получение аналитических выводов и повысить самостоятельность бизнес-пользователей. Настоящая работа посвящена разработке ИИ-ассистента для аналитики данных с использованием больших языковых моделей (LLM). Отдельный акцент в работе сделан на методах инжиниринга контеста LLM с использованием подхода Retrieval-Augmented Generation (RAG). Показано, как при помощи динамических методов гибридного векторного поиска можно добиться снижения стоимости генерации SQL запросов при сохранении приемлемого качества результата. Работа выполнена в виде программного продукта развернутого в публичном хостинге, обладающем удобным пользовательским интерфейсом и предоставляющим пользователю возможность выполнять запросы по аналитике данных в удаленном облачном хранилище.

# Введение

На протяжении многих лет извлечение количественных показателей из корпоративных хранилищ оставалось доступным только специалистам с навыками SQL и пониманием схемы хранилища. Такая ситуация формировала характерную организационную цепочку, в которой бизнес-вопрос проходил по маршруту «аналитик подразделения → BI-разработчик → инженер данных» и приводил к получению ответа спустя дни, а порой и недели. Для современного темпа управленческих решений длительность этого цикла оказалась неприемлемой, что и сформировало запрос на технологии, способные «понимать» вопрос пользователя на естественном языке и самостоятельно превращать его в исполнимый код.

Развитие больших языковых моделей (Large Language Models, далее — LLM) предоставило техническую базу для подобной автоматизации: умение моделей рассуждать в контексте позволило им преобразовывать вопросы пользователя непосредственно в SQL-выражения. Возникшая на стыке NLP и баз данных дисциплина Text-to-SQL переживает заметный рост, что подтверждается серией появившихся бенчмарков — от классического Spider 1.0 до промышленно-ориентированных BIRD и Spider 2.0. Парадокс заключается в том, что успехи на ранних бенчмарках (свыше 90 % точности) не транслируются в реалистичные сценарии: на Spider 2.0 даже самые мощные агенты на сегодня преодолевают порог лишь 30–35 % gold-match accuracy.

Основанием для столь большого разрыва служит набор особенностей, отсутствовавших в академических бенчмарках первого поколения, но повсеместно встречающихся в промышленной эксплуатации: сотни таблиц со множеством столбцов, тяжёлые вложенные типы (`VARIANT` Snowflake, `STRUCT`/`ARRAY` BigQuery), временное шардирование данных, а также неявные семантические связи, для понимания которых требуется владение конкретной доменной областью. Передача всей DDL подобного хранилища в контекст LLM зачастую упирается в физический предел контекстного окна, а в случаях, когда такой предел не нарушается, размытие внимания модели на нерелевантные элементы заметно снижает качество.

**Объектом исследования** выступают подходы к автоматизированному синтезу SQL-кода, опирающиеся на крупные языковые модели и применяемые на промышленных схемах данных.

**Предмет исследования** — архитектура динамического Retrieval-Augmented Generation (RAG), при которой в контекст LLM попадает только тот фрагмент метаданных, который релевантен текущему пользовательскому запросу.

**Цель работы** состоит в проектировании и экспериментальной проверке программного комплекса, в основе которого лежит гибридный векторный поиск по метаданным схемы, обеспечивающий одновременно рост точности генерации SQL и снижение её токеноёмкости на бенчмарке Spider 2.0 — Snow.

**Задачи исследования:**

1. Провести аналитический обзор современных методов Text-to-SQL и выявить ключевые ограничения существующих агентных решений (DSR-Lite, ReFoRCE, Spider-Agent).
2. Спроектировать структуру векторной базы знаний, отражающую все существенные сущности схемы базы данных: таблицы, столбцы, связи, семантические факты, образцы данных, синтаксические шаблоны.
3. Разработать гибридный алгоритм извлечения, сочетающий плотный семантический поиск (dense) и лексический поиск (BM25) с агрегацией методом Reciprocal Rank Fusion (RRF).
4. Спроектировать детерминированный компилятор Plan → SQL, отделяющий рассуждение LLM от форматирования итогового SQL-кода.
5. Реализовать цикл самокоррекции (repair loop) с классификацией ошибок и направленным обращением к справочной информации.
6. Провести сравнительные эксперименты с тремя открытыми реализациями (DSR-Lite, Spider-Agent, ReFoRCE) на одинаковых выборках бенчмарка Spider 2.0 — Snow.
7. Провести исследование абляции для оценки вклада каждого ключевого компонента в итоговую точность.
8. Реализовать пользовательский интерфейс (веб-приложение), демонстрирующий применимость подхода в режиме промышленной эксплуатации.

**Научная новизна работы.** В работе предложена архитектура **сущностно-ориентированного RAG для задач Text-to-SQL**, в которой каждый документ индекса представляет собой обособленный метаданный элемент — таблицу, столбец, связь или семантический факт, — а не текстовый фрагмент фиксированной длины. Введён обязательный шаг предварительного **сворачивания партиционных таблиц** при формировании индекса, что исключает шум от временных шардов в результатах поиска. Спроектирован **детерминированный компилятор Plan → SQL**, ориентированный на специфику Snowflake (`LATERAL FLATTEN`, доступ к `VARIANT`, конвейеры CTE) и снимающий с LLM ответственность за форматирование выходного кода. Перечисленные элементы интегрированы в единый агентский цикл с самокоррекцией.

**Практическая значимость.** Получившийся программный комплекс, размещённый в публичной облачной среде, на бенчмарке Spider 2.0 — Snow демонстрирует **87 %** gold-match accuracy на 100-запросной подвыборке при стоимости **порядка \$0,38 на правильный ответ** (модель `gpt-5.4-mini`). По сравнению с эталонной реализацией ReFoRCE на тех же данных и той же модели это даёт **выигрыш в точности в 4,2 раза и снижение стоимости правильного ответа в 18 раз**. Достигнутые экономические показатели делают разработку пригодной к промышленной эксплуатации в качестве встраиваемого «помощника аналитика» — компонента BI-платформ и корпоративных дашбордов.

**Положения, выносимые на защиту:**

1. Сущностно-ориентированный RAG со специализированными коллекциями метаданных одновременно повышает gold-match accuracy и снижает токеноёмкость по сравнению с агентными решениями, использующими целиком DDL в промпте.
2. Сворачивание партиционных таблиц при формировании индекса является необходимым условием применимости RAG к доменам с временным шардированием (GA360, GA4).
3. Детерминированный компилятор Plan → SQL снимает целый класс синтаксических ошибок и делает выходной SQL воспроизводимым вне зависимости от вариативности LLM-кандидатов.
4. Гибридный поиск (dense + lexical через RRF) превосходит каждый из методов в отдельности в задачах, где имена-идентификаторы и естественноязычные описания дополняют друг друга.

**Апробация и публикации.** Этапные результаты работы фиксировались в журнале архитектурных изменений (`docs/architecture/`); итоговый бенчмарк-отчёт размещён в каталоге `docs/benchmarks/`. Исходный код опубликован в открытом репозитории под лицензией MIT, что обеспечивает полную воспроизводимость заявленных результатов.

**Структура работы.** Глава 1 содержит аналитический обзор современных методов Text-to-SQL и выявляет ключевые ограничения. Глава 2 формулирует постановку задачи. Глава 3 описывает структуру векторной базы знаний (пять специализированных коллекций). Глава 4 раскрывает алгоритм гибридного извлечения. Глава 5 представляет архитектуру агента-исполнителя SQL: компилятор Plan → SQL, Best-of-N, цикл самокоррекции. Глава 6 содержит сравнительные результаты бенчмарков; Глава 7 — исследование абляции; Глава 8 — заключение. Список литературы содержит 17 наименований, приложение — описание программной архитектуры и пользовательского интерфейса.

# 1. Исследование предметной области

## 1.1. Общая постановка задачи преобразования текста в запросы SQL

Задача преобразования текста в SQL (Text-to-SQL) заключается в автоматической генерации корректного SQL-запроса по текстовому описанию на естественном языке (Natural Language, NL).

Формально задача может быть представлена как отображение:

$$
f:\left(Q_{NL},\,S,\,D\right)\rightarrow Q_{SQL}
$$

где $Q_{NL}$ — текст запроса пользователя, $S$ — схема базы данных, $D$ — дополнительные метаданные (описания таблиц и колонок с комментариями, примеры значений, документация), а $Q_{SQL}$ — корректный и работающий SQL-запрос.

Исторически задача решалась посредством семантического парсинга, однако с появлением больших языковых моделей (LLM) произошёл переход к генеративным подходам с использованием LLM.

## 1.2. Ранние LLM-подходы: zero-shot и промпт-инжиниринг

С развитием и улучшением качества LLM исследователи начали изучать их применимость к задачам Text-to-SQL путем формирования сложных, так называемых zero-shot и few-shot промптов. Здесь необходимо пояснить, что под устойчивым термином zero-shot понимается запрос к LLM, не содержащий правильного ответа, а few-shot промпт — это запрос с одной или несколькими подсказками правильного ответа для LLM.

Работа C3 (Zero-shot Text-to-SQL with ChatGPT) [1] продемонстрировала, что тщательно подобранные подсказки (prompt engineering), структурирование входа и контроль формата вывода позволяют существенно повысить точность без дополнительного обучения модели. Авторы выделили три ключевых компонента:

- ясная структуризация схемы базы данных в подсказке;
- использование согласованных примеров;
- жёсткий контроль формата SQL-ответа.

Похожие идеи систематически развиты в работе DAIL-SQL [2], где предложен интегрированный prompting-pipeline с динамическим выбором примеров. Эти исследования показали, что грамотный prompt-инжиниринг может обеспечить высокое значение метрики accuracy на бенчмарке Spider 1.0.

Однако данные методы сталкиваются с рядом ограничений:

- рост сложности схем и длинного контекста;
- галлюцинации имен таблиц и атрибутов;
- чувствительность к формулировке запроса.

## 1.3. Расширение бенчмарков: BIRD и Spider 2.0

С ростом возможностей LLM возникла необходимость более реалистичных бенчмарков. Работа BIRD (Big Bench for Large-Scale Database Grounded Text-to-SQL) [3] предложила масштабный набор данных, ориентированный на привязку к содержимому базы данных, использование внешних знаний а также генерацию более сложных запросов. BIRD выявил, что высокая точность на Spider не гарантирует устойчивости при увеличении размера и сложности базы данных.

Следующим шагом стал бенчмарк Spider 2.0 [4], ориентированный на реальные промышленные сценарии. В отличие от предыдущих бенчмарков, Spider 2.0 имеет следующие особенности:

- требует работы с длинным контекстом (документация, dbt-проекты);
- предполагает многошаговую генерацию;
- включает задачи уровня реалистичной промышленной среды.

Авторы показали, что даже продвинутые LLM-агенты решают лишь ограниченную долю задач, что указывает на необходимость новых архитектурных решений.

## 1.4. Снижение галлюцинаций и выравнивание задачи

Одной из ключевых проблем LLM в Text-to-SQL является галлюцинация — генерация несуществующих таблиц, столбцов, либо некорректных синтаксических конструкций.

В работе TA-SQL [5] предложен метод предварительного выравнивания задач (task alignment), который улучшает способность модели к обобщению путём поиска аналогичных задач и структур. Авторы классифицируют типы галлюцинаций и демонстрируют улучшения на BIRD.

Работа OpenSearch-SQL [6] развивает идею динамического few-shot обучения и согласованного выравнивания решений (consistency alignment), моделируя процесс работы человека-аналитика, который сначала уточняет доступные структуры БД, а затем с учетом этих знаний создает SQL запрос.

Данные исследования демонстрируют переход от статического prompt-инжиниринга к более адаптивным и устойчивым стратегиям генерации.

## 1.5. Многошаговые рассуждения и агентные решения

Работа CHASE-SQL [7] предложила стратегию многошагового рассуждения (multi-path reasoning): модель генерирует несколько SQL кандидатов, которые затем проходят оптимизированный отбор.

Для Spider 2.0 особенно значима работа ReFoRCE [8], где реализован агентный цикл:

- компрессия схемы данных (database information compression);
- итеративное исследование столбцов;
- генерация нескольких вариантов;
- голосование и самокоррекция.

Дальнейшим развитием агентного направления стала работа APEX-SQL [14], в которой предложен переход от статической компиляции запроса к агентному исследованию данных (agentic exploration). В основу подхода положен цикл последовательной проверки гипотез, при котором ИИ модель не только использует метаданные схемы таблиц базы данных (БД), но также на этапе генерации запроса выполняет профилирование даных и проверяет свои гипотезы в режиме реального времени. Это позволяет находить дополнительные связи и зависимости между атрибутами схемы и уточнять семантику запроса последовательно улучшая качество результирующего SQL.

## 1.6. Масштабирование данных и обучение с подкреплением

Параллельно вышеописанным подходам развивалось направление по использованию методов обучения с подкреплением и улучшения обучающих данных.

В работе OmniSQL [9] предложен масштабируемый синтез большого количестсва Text-to-SQL датасетов (порядка одного миллиона), что позволяет улучшить покрытие шаблонов и повысить переносимость моделей.

Работа Reasoning-SQL [10] использует обучение с подкреплением (GRPO) и частичные награды:

- награда за корректную привязку схемы базы данных (schema linking);
- проверка синтаксиса;
- семантическая близость.

Такой подход снижает проблему разреженности награды и повышает способность модели к пошаговому рассуждению (reasoning).

В работе Automatic Metadata Extraction [11] исследуется автоматическое извлечение описаний таблиц и статистик базы данных для улучшения генерации SQL. Это особенно актуально для Spider 2.0, где метаданные не всегда даны в явном виде.

Работа SWE-SQL [12] расширяет задачу до диагностики и исправления SQL-запросов, отражая реальные производственные сценарии.

Дополнительно в литературе отмечаются проблемы корректности аннотаций бенчмарков, что показано в исследовании CIDR 2026 [13], где выявлены несоответствия в BIRD и Spider 2.0.

## 1.7. Проблемы существующих решений

Несмотря на достигнутые успехи, современные методы преобразования естественного языка в SQL-запросы по-прежнему ограничены рядом архитектурных факторов. Традиционные стратегии zero-shot и few-shot критически зависят от объема и структуры метаданных, передаваемых в промпте. С увеличением масштаба баз данных и усложнением пользовательских инструкций эффективность таких подходов падает, что подтверждается результатами бенчмарка Spider 2.0. В реальных условиях промышленной эксплуатации модели сталкиваются с необходимостью анализа не только таблиц, но и сопутствующего программного кода, а также проектной документации. В производственных системах больших данных (Big Data) хранилища и озера данных могут содержать сотни таблиц и тысячи атрибутов. Передача такого объема метаданных для анализа в большую языковую модель создает проблему «перегруженного контекста» и часто сталкивается с ограничениями размера контекстного окна.

Попытки преодолеть эти барьеры привели к созданию агентских систем и методов масштабирования на этапе вывода (test-time scaling), как, например, во фреймворки APEX-SQL и ReFoRCE. Данные решения обеспечивают прирост точности за счет многократных итераций, фильтрации признаков и верификации гипотез через выполнение SQL-кода. Тем не менее, повышение качества ответов здесь достигается путем значительного усложнения инференса: многошаговые рассуждения и генерация множества вариантов запроса увеличивают вычислительные затраты, в том числе выраженные в количестве потребляемых токенов. Для корпоративных систем с интенсивным потоком обращений итоговая стоимость владения подобными решениями часто оказывается неприемлемой.

# 2. Постановка задачи исследования

В рамках данного исследования предлагается рассмотреть альтернативную возможность использования архитектуры Retrieval-Augmented Generation (RAG) для оптимизации содержимого контекста LLM. Основная гипотеза работы заключается в том, что RAG способен не только повысить релевантность ответов за счет продвинутых методов гибридного векторного поиска, но и снизить общее потребление токенов путем отсечения информации нерелевантной для пользовательского запроса.

Вместо избыточной передачи всей схемы данных, механизм RAG позволяет выборочно интегрировать в запрос лишь необходимые элементы: конкретные атрибуты таблиц, примеры кортежей и подходящие синтаксические шаблоны. Такой подход минимизирует объем контекстного окна, снижая потребление токенов без существенной потери качества.

Актуальность данного вектора развития подтверждается современными трендами в области решений уровня предприятий (enterprise solutions), где уточненное извлечение информации признается ключевым фактором масштабируемости систем Text-to-SQL. Ярким примером промышленной реализации этой концепции стали решения от лидеров рынка облачных данных (lakehouse) Databricks и Snowflake. В частности, инструмент Databricks AI Functions и специализированный ИИ помощник Genie используют механизмы семантического поиска по метаданным, чтобы предоставлять контекстно-зависимые ответы на бизнес-запросы. Аналогично, интеграция модуля Cortex AI в экосистему Snowflake позволяет конечным пользователям взаимодействовать с данными через «умные» интерфейсы, где RAG-архитектура обеспечивает точность трансляции естественного языка в команды языка SQL без необходимости передачи всей структуры хранилища в LLM. Появление таких «помощников» (AI Assistants) напрямую в интерфейсах аналитических платформ подтверждает переход индустрии к гибридным методам генерации, сочетающим извлечение знаний и агентские подходы в рассуждениях.

Практическим результатом данной дипломной работы является разработка программного продукта — интеллектуального ассистента, предназначенного для демократизации доступа к данным в удаленном облачном хранилище. Система выступает в роли посредника между конечным пользователем и сложной структурой базы данных, преобразуя запросы пользователя на естественном языке в синтаксически корректные SQL-выражения. Благодаря предварительному обучению системы и реализации описанных выше механизмов гибридного RAG с продвинутыми техниками извлечения метаданных, ассистент обеспечивает высокую точность обработки транзакций даже при работе с распределенными хранилищами, характеризующимися высокой задержкой и значительным объемом неявных связей. Также за счет использования RAG мы добиваемся снижения использования токенов по сравнению с описанными ранее решениями при сохранении приемлемого качества генерации.

Разработанный программный продукт может быть успешно интегрирован в существующие бизнес-процессы в качестве интерфейса «человек-данные». Пользователь получает возможность извлекать аналитические срезы, не обладая навыками программирования, а также избегая необходимости обращения к техническим специалистам ИТ.

Программная реализация включает в себя модули динамического поиска релевантных сегментов метаданных по векторной базе знаний, блок верификации сгенерированных запросов, слой взаимодействия с API облачного провайдера Snowflake, а также удобный пользовательский интерфейс. Таким образом, работа не только решает практическую задачу снижения стоимости использования LLM при сохранении качества генерации, но и предлагает готовый прикладной инструмент, масштабируемый под реальные промышленные задачи прикладного характера.

# 3. Описание структуры векторной базы данных

## 3.1. Описание коллекций векторной базы данных RAG-системы

### 3.1.1. Общая характеристика хранилища

В качестве векторной базы данных используется ChromaDB — встраиваемое хранилище с поддержкой персистентного хранения на диске. Каталог хранения: `rag_snow_agent/.chroma/`. Для вычисления векторных представлений (эмбеддингов) используется модель `text-embedding-3-large` компании OpenAI, генерирующая вектора размерностью 3072. В качестве метрики сходства применяется косинусное расстояние.

Хранилище организовано в пять тематических коллекций, каждая из которых выполняет определённую функцию в процессе генерации SQL-запросов.

### 3.1.2. Коллекция `schema_cards` (622 элемента)

**Назначение.** Основная база знаний системы, содержащая структурированные описания объектов схемы данных — таблиц, столбцов и связей между таблицами. Используется на этапе контекстного извлечения для формирования компактного представления схемы (SchemaSlice), которое включается в промпт языковой модели.

**Типы хранимых записей:**

**TableCard — карточка таблицы.** Для каждой таблицы базы данных создаётся одна карточка. Партиционированные таблицы (например, ежедневные таблицы Google Analytics формата `GA_SESSIONS_YYYYMMDD`, насчитывающие 366 отдельных таблиц) объединяются в одну репрезентативную запись. В качестве имени используется реально существующая в Snowflake таблица последней партиции, а в описание включается информация о диапазоне дат и способе фильтрации.

Текстовое представление (документ) включает имя таблицы, описание на естественном языке и список столбцов. Описание генерируется моделью GPT-5.4 на основе профилирования 100 строк реальных данных, что обеспечивает семантически осмысленный поиск: запрос пользователя о «выручке» будет сопоставлен с таблицей, в описании которой упоминаются транзакционные данные.

Метаданные: идентификатор базы данных (`db_id`), квалифицированное имя таблицы, описание на естественном языке, оценка количества токенов.

**ColumnCard — карточка столбца.** Для каждого столбца создаётся отдельная запись, включая столбцы вложенных полей типа VARIANT. Описания столбцов генерируются на основе статистического профиля данных (доля пустых значений, диапазон значений, количество уникальных значений, структура вложенных объектов) и содержат указания по корректному построению SQL-запросов.

Для столбцов типа VARIANT описание включает классификацию структуры — ARRAY (требуется оператор `LATERAL FLATTEN`) или OBJECT (используется доступ через двоеточие), а также перечень известных вложенных полей с указанием их типов данных.

Вложенные поля VARIANT-столбцов (например, `"totals":pageviews`) хранятся с типом данных `VARIANT_FIELD` и содержат в метаданных признак источника обнаружения — через прямой вызов `OBJECT_KEYS()` (объектная структура) или через `LATERAL FLATTEN + OBJECT_KEYS()` (элемент массива). Этот признак определяет классификацию родительского столбца при формировании промпта.

**JoinCard — карточка связи.** Для каждой обнаруженной связи между таблицами создаётся запись, содержащая левую и правую таблицы, столбцы соединения, уровень уверенности (1.0 для внешних ключей, 0.7 для эвристических совпадений) и источник обнаружения.

### 3.1.3. Коллекция `semantic_cards` (5 762 элемента)

**Назначение.** Хранилище семантических фактов, выведенных из метаданных схемы с помощью детерминированных эвристик. Используется для обогащения контекста промпта дополнительными подсказками о структуре и семантике данных.

**Типы семантических фактов:**

- **`primary_time_column`** — столбцы с типами `DATE`, `TIMESTAMP` и их разновидностями. Позволяет системе автоматически определять временные измерения.
- **`date_format_pattern`** — столбцы с датоподобными именами и числовым или текстовым типом. Классифицируются как «YYYYMMDD целое число» (для числовых столбцов) или «YYYYMMDD строка» (для текстовых). Эта информация критична для корректной генерации условий фильтрации по дате.
- **`metric_candidate`** — числовые столбцы, имена которых указывают на метрическое содержание (`revenue`, `count`, `price`, `total` и т. д.).
- **`dimension_candidate`** — текстовые столбцы с именами, характерными для аналитических измерений (`source`, `country`, `category`, `status` и т. д.).
- **`nested_container_column`** — столбцы типов `VARIANT`, `OBJECT` и `ARRAY` с указанием классификации структуры и известных вложенных полей.
- **`identifier_column`** — столбцы, соответствующие шаблонам идентификаторов (`*_ID`, `*_KEY`, `ID`). Используются для защиты от удаления при оптимизации бюджета токенов.

Каждый факт сопровождается уровнем уверенности (от 0.0 до 1.0) и указанием источника (метаданные, эвристики, зонды).

### 3.1.4. Коллекция `sample_records` (10 элементов)

**Назначение.** Хранение образцов данных из таблиц для включения в контекст промпта. Каждый элемент содержит 2–5 строк из одной таблицы, отформатированных в виде компактного JSON.

Образцы данных позволяют языковой модели «увидеть» реальные значения столбцов, понять формат дат, структуру вложенных VARIANT-объектов и типичные диапазоны значений. Это особенно важно для таблиц со сложной структурой, таких как Google Analytics, где столбец `hits` содержит массив вложенных объектов с десятками полей.

### 3.1.5. Коллекция `trace_memory` (5 элементов)

**Назначение.** Хранение успешных решений для контекстного обучения на примерах (few-shot learning). При успешном решении задачи система сохраняет пару «вопрос — план решения» для последующего использования в качестве примера при решении семантически близких задач.

Документ содержит краткое изложение вопроса и плана решения. Метаданные включают идентификатор базы данных, идентификатор экземпляра задачи и список использованных таблиц. Поиск выполняется по семантической близости к текущему вопросу с фильтрацией по базе данных.

Данный механизм реализует принцип «обучения на собственном опыте»: система накапливает библиотеку успешных решений и использует их для повышения качества генерации на аналогичных задачах.

### 3.1.6. Коллекция `snowflake_syntax` (55 элементов)

**Назначение.** Справочник синтаксиса Snowflake SQL, используемый на этапе исправления ошибок в сгенерированных запросах. Содержит фрагменты документации по синтаксису различных конструкций: соединения таблиц (JOIN), оператор `LATERAL FLATTEN`, оконные функции, операции с типами данных и другие.

При возникновении ошибки компиляции или выполнения SQL-запроса система формирует поисковый запрос из текста ошибки и фрагмента SQL, извлекает релевантные справочные фрагменты и включает их в промпт для исправления. Это позволяет модели использовать точную справочную информацию о синтаксисе Snowflake вместо генерации исправлений «по памяти».

## 3.2. Процесс наполнения коллекций

**Индексирование схемы (онлайн).** Выполняется при подключении к Snowflake. Извлекает таблицы, столбцы, типы данных и связи из `INFORMATION_SCHEMA`. Для VARIANT-столбцов выполняет зондирование структуры через `OBJECT_KEYS()` и `LATERAL FLATTEN`. Партиционированные таблицы объединяются в одного представителя.

**Профилирование данных (офлайн).** Для каждой таблицы извлекается 100 строк данных, вычисляется статистический профиль каждого столбца, затем модель GPT-5.4 генерирует текстовые описания таблиц и столбцов на естественном языке. Описания сохраняются в файл `table_column_descriptions.json` и загружаются в коллекцию `schema_cards` через скрипт обогащения `enrich_descriptions.py`.

**Семантические факты (автоматически).** Генерируются детерминированными эвристиками на основе типов данных, имён столбцов и результатов зондирования VARIANT-структур.

## 3.3. Использование коллекций в процессе генерации SQL

На каждый пользовательский запрос система обращается к коллекциям в следующем порядке:

1. **`schema_cards`** — гибридный поиск (семантический + лексический + RRF-слияние) для извлечения релевантных таблиц и столбцов. Результат: SchemaSlice с бюджетом до 10 000 токенов.
2. **`semantic_cards`** — извлечение семантических фактов для обогащения контекста (форматы дат, кандидаты на метрики, классификация VARIANT-структур).
3. **`sample_records`** — извлечение образцов данных для релевантных таблиц.
4. **`trace_memory`** — поиск семантически близких успешных решений для формирования контекста few-shot.
5. **`snowflake_syntax`** — обращение только при возникновении ошибок на этапе исправления SQL-запросов.

# 4. Процесс извлечения информации (Retrieval Pipeline)

## 4.1. Стратегия разбиения на фрагменты (Chunking)

В отличие от классических RAG-систем, работающих с произвольными текстовыми документами, данная система оперирует структурированными метаданными схемы базы данных. Вместо разбиения документа на фрагменты фиксированного размера применяется стратегия «один объект — один фрагмент» (entity-level chunking):

- **TableCard** — один фрагмент на таблицу. Документ включает квалифицированное имя (`DB.SCHEMA.TABLE`), описание на естественном языке, список столбцов, временные столбцы и ключи соединения. Типичный размер: 60–300 токенов.
- **ColumnCard** — один фрагмент на столбец. Документ содержит квалифицированное имя столбца, тип данных и описание. Для VARIANT-столбцов описание включает способ доступа к вложенным полям и их перечень. Типичный размер: 20–400 токенов (зависит от сложности описания).
- **JoinCard** — один фрагмент на связь между таблицами. Документ описывает левую и правую стороны связи с указанием уровня уверенности. Типичный размер: 20–40 токенов.

Такая стратегия обеспечивает точную атомарность извлечения: система может извлечь конкретный столбец или конкретную таблицу, не загружая избыточный контекст.

Для партиционированных таблиц применяется предварительное объединение (partition collapsing): например, 366 ежедневных таблиц представляющей годовые данные сводятся к одной репрезентативной карточке, что исключает дублирование в результатах поиска и экономит бюджет контекста.

## 4.2. Этап 1: Плотный семантический поиск (Dense Retrieval)

Первый этап работы ретривера опирается на векторные представления карточек, получаемые с помощью модели `text-embedding-3-large`. Текст пользовательского вопроса $Q_{NL}$ переводится в 3072-мерное вещественное представление, и далее в ChromaDB выполняются два независимых запроса: за $K_{table}=25$ ближайшими табличными карточками и за $K_{col}=100$ ближайшими карточками столбцов. Расстояние оценивается по косинусной мере:

$$
\mathrm{sim}_{\cos}(\mathbf{q},\mathbf{d})=\frac{\mathbf{q}\cdot\mathbf{d}}{\lVert\mathbf{q}\rVert\,\lVert\mathbf{d}\rVert}
$$

где $\mathbf{q}$ — векторное представление запроса, $\mathbf{d}$ — векторное представление карточки.

**Сильные стороны плотного поиска применительно к нашей задаче:**

1. *Сопоставление по смыслу, а не по точным словам.* Например, запрос «общий доход за квартал» успешно находит колонку `revenue_amount_usd`, описание которой содержит «выручка от продаж в долларах США», — несмотря на отсутствие в имени колонки слов «доход» и «квартал».
2. *Использование подробных описаний.* Тексты, сгенерированные моделью GPT-5.4 по результатам профилирования реальных данных, насыщают эмбеддинги доменной семантикой — например, прямо указывают на принадлежность таблицы к классу «логов веб-аналитики».
3. *Стабильность относительно синонимии.* Морфологические альтернативы вроде «продажи», «выручка», «доход» оказываются близкими точками в векторном пространстве, что устраняет зависимость от конкретной формулировки пользователя.

**Где плотный поиск уступает другим методам.** Если запрос содержит короткий идентификатор или специфический код — `fullVisitorId`, `geo_id`, `5713D`, `Q1095` — то соответствующая лексема расплывается в эмбеддинговом пространстве и теряет вес ранжирования. Точно так же плотный поиск с трудом разводит карточки с похожим описанием, но различающиеся по точному имени, тогда как пользовательский запрос ссылается именно на конкретное имя.

Реализация представлена классом `HybridRetriever` в модуле `rag_snow_agent/src/rag_snow_agent/retrieval/hybrid_retriever.py`; за плотный этап отвечает метод `_dense_query()`. Возвращается упорядоченный список объектов `ScoredItem` с полями `dense_rank` (позиция) и значением косинусной близости.

## 4.3. Этап 2: Лексический поиск (Sparse Retrieval)

Лексический проход призван компенсировать слабости плотного — он отвечает за точное совпадение ключевых лексем. Применяется ранжирующая функция **BM25** (Best Matching 25), стандартная для информационного поиска [16]:

$$
\mathrm{BM25}(D, Q) = \sum_{t \in Q} \mathrm{IDF}(t)\cdot\frac{f(t,D)\cdot(k_1+1)}{f(t,D)+k_1\cdot\bigl(1 - b + b\cdot\dfrac{|D|}{\mathrm{avgdl}}\bigr)}
$$

где $f(t,D)$ — частота терма $t$ в документе $D$, $|D|$ — длина документа в токенах, $\mathrm{avgdl}$ — средняя длина документа по индексу, $\mathrm{IDF}(t)$ — обратная документная частота терма, а $k_1$ и $b$ — настраиваемые параметры; в работе использованы значения по умолчанию: $k_1=1.5$, $b=0.75$.

**Адаптация BM25 под специфику Text-to-SQL.**

1. *Дробление составных идентификаторов.* Имя столбца вроде `revenue_amount_usd` индексируется и целиком, и по компонентам `revenue`, `amount`, `usd`. Благодаря этому формула одновременно срабатывает и при естественноязычной формулировке запроса, и при цитировании пользователем точного имени поля.
2. *Нечувствительность к регистру при сохранении оригинала.* Токенизатор приводит идентификаторы к нижнему регистру и расценивает символы `_`, `.`, `:` как разделители, однако оригинальная форма имени также сохраняется — это нужно, чтобы запрос с прямой цитатой кода точно попадал в нужный документ.
3. *Усиленный вес редких терминов.* Низкочастотные ключевые слова — `wikidata`, `osm_id`, `Q1095` — получают большой $\mathrm{IDF}$ и доминируют в ранжировании. Такая особенность даёт прицельный поиск по специфическим маркерам, на которые плотный этап реагирует слабо.

Лексический проход вычисляется параллельно плотному и возвращает аналогичный по структуре список `ScoredItem` с полями `bm25_score` и `lexical_rank`. Соответствующий метод — `_lexical_query()` всё того же `HybridRetriever`; в основе лежит open-source-библиотека `rank_bm25`.

## 4.4. Этап 3: Слияние результатов методом RRF (Reciprocal Rank Fusion)

Финальная свёртка результатов двух этапов выполняется методом **Reciprocal Rank Fusion** [15]. Это лёгкий приём агрегации ранжированных списков, устойчивый к разнородности оценок исходных алгоритмов:

$$
\mathrm{RRF\_score}(d) = \sum_{r \in R} \frac{1}{k + \mathrm{rank}_r(d)}
$$

где:

- $R$ — набор ранжированных списков (в нашем случае их два — dense и lexical),
- $\mathrm{rank}_r(d)$ — позиция документа $d$ в списке $r$ (нумерация с единицы),
- $k$ — параметр сглаживания, для которого принято значение $k = 60$.

Роль параметра $k$ заключается в балансировке: при $k = 60$ объекты, занимающие высокие позиции одновременно в обоих списках, получают ощутимый бонус, но при этом объект, попавший только в один список, не выбрасывается из выдачи.

**Чем RRF предпочтительнее линейной комбинации исходных скоров.** Косинусная мера и оценка BM25 имеют различную природу и не приведены к единой шкале. Чтобы напрямую сложить эти оценки, потребовалось бы калибровать веса под каждую базу данных в отдельности, что плохо масштабируется на 20 различающихся доменов Spider 2.0 — Snow. RRF оперирует исключительно позициями в списках и не зависит от абсолютных значений сходства, что и обеспечивает устойчивость метода между доменами. На практике именно эта характеристика делает RRF удачным выбором для задач, где плотный и лексический сигналы оказываются дополняющими друг друга.

**Что получаем на выходе.** Сводный список карточек, отсортированный по убыванию RRF-оценки. У каждой записи сохраняются её позиция в исходных проходах (`dense_rank`, `lexical_rank`), агрегированная позиция (`fused_rank`) и собственно `rrf_score`. Далее этот список передаётся в три последовательных этапа обработки: усечение по бюджету токенов, расширение по графу соединений (`expand_join_graph_neighbors`) и обогащение полями типа `VARIANT` (`_enrich_variant_fields`).

## 4.5. Управление бюджетом токенов и постобработка SchemaSlice

Передача сводного ранжированного списка в промпт «как есть» противоречила бы основной идее работы — сократить контекст. Поэтому после RRF-слияния список проходит через цепочку постобработок, превращающую его в финальную структуру `SchemaSlice`:

**Шаг 1: Расширение по графу соединений.** Процедура `expand_join_graph_neighbors` обходит упорядоченный список таблиц и добавляет в него «1-hop соседей» по графу `JoinCard`, если такие соседи действительно нужны для исполнения запроса. Например, если в выборку попала `ORDERS`, а между ней и `CUSTOMERS` зафиксирован внешний ключ, то `CUSTOMERS` будет добавлена автоматически. Этот шаг страхует от типичной ситуации, при которой ретривер успешно находит «главную» таблицу запроса, но не обнаруживает вспомогательные, без которых соединение не построить.

**Шаг 2: Обогащение полей `VARIANT`.** Для каждой колонки соответствующего типа в коллекцию `schema_cards` отправляется отдельный запрос за вложенными подполями (тип `VARIANT_FIELD`); найденные подполя прикрепляются к карточке родительской колонки. Кроме того, по признаку источника обнаружения (`OBJECT_KEYS()` напрямую либо `LATERAL FLATTEN + OBJECT_KEYS()`) колонка маркируется как объектная или массивная. Если эту классификацию выполнить неверно, выходной SQL гарантированно сломается на этапе компиляции Snowflake: попытка `LATERAL FLATTEN` над объектом либо доступ через `:field` к элементу массива не пройдут синтаксическую проверку.

**Шаг 3: Усечение по бюджету токенов.** Размер итогового `SchemaSlice` ограничен параметром `max_schema_tokens = 10 000`. Процедура `trim_to_budget` стартует с полного списка и удаляет наименее ранжированные элементы (по `fused_rank`) до тех пор, пока сумма токенов не окажется в пределах лимита. Удаление защищено двумя гарантиями:

- *Сохранность идентификаторов.* Колонки с семантическим маркером `identifier_column` (имена с суффиксами `_ID`, `_KEY`) никогда не удаляются из таблиц, попавших в выборку, — иначе LLM лишится возможности построить корректные соединения.
- *Сохранность временных колонок.* Колонки, помеченные как `primary_time_column`, оставляются по одной на каждую отобранную таблицу: фильтрация по дате является самой частой операцией в аналитических SQL-запросах, и потеря этих колонок резко повышает риск неудачи генерации.

**Шаг 4: Сериализация для промпта.** Финальный `SchemaSlice` оформляется в Markdown-блок: имена таблиц, описания, перечень колонок с типами и подсказками. Полученный блок составляет динамическую часть системного промпта; в свою очередь, статическая часть содержит общие инструкции по диалекту Snowflake и формату ожидаемого ответа.

# 5. Архитектура агента генерации SQL

## 5.1. Общий контур цикла обработки запроса

Когда ретривер (Глава 4) собрал актуальный `SchemaSlice` для конкретного пользовательского запроса, эстафету подхватывает агент генерации SQL. Перед ним стоит задача синтезировать корректный, исполнимый и семантически осмысленный запрос на диалекте Snowflake, опираясь на структурированное представление схемы и текст вопроса.

Работа агента организована в виде последовательности из пяти стадий:

1. **Декомпозиция вопроса** на подзадачи — выполняется опционально, для запросов с явной многошаговой логикой.
2. **Параллельная генерация $N$ кандидатов плана** в виде структурированного объекта `QueryPlan` (валидируется через Pydantic).
3. **Детерминированная сборка SQL по плану** с учётом синтаксиса Snowflake (`LATERAL FLATTEN`, обращение к `VARIANT`, многоступенчатые CTE).
4. **Цикл самокоррекции** (repair loop), в котором ошибочный SQL пропускается через классификатор, после чего формируется специализированный repair-промпт.
5. **Верификация полученного результата** — либо в режиме бенчмарка против эталонной выгрузки, либо в production-режиме через возврат пользователю.

Идея, лежащая в основе этой декомпозиции, — переложить на LLM ровно то, в чём она сильна (понимание естественного языка, восстановление доменной семантики), и забрать у неё то, в чём она ненадёжна (точное форматирование SQL, стабильное цитирование идентификаторов, отсутствие галлюцинаций имён).

## 5.2. Детерминированный компилятор Plan → SQL

Ядром инженерной части работы стало разграничение зон ответственности: LLM формирует только высокоуровневое описание запроса, а итоговый SQL собирает кодогенератор. От LLM требуется выдать структурированный JSON-объект, валидируемый моделью `QueryPlan` библиотеки Pydantic:

```json
{
  "selected_tables": ["GA360.GA_SESSIONS_*"],
  "joins": [],
  "filters": [{"column": "date", "op": ">=", "value": "20170701"}],
  "aggregations": [{"function": "COUNT", "expression": "DISTINCT visitorId"}],
  "group_by": [],
  "order_by": [{"expression": "1", "direction": "DESC"}],
  "limit": 10
}
```

За преобразование плана в исполнимый код отвечает функция `compile_plan(plan, schema_slice)` из модуля `rag_snow_agent.prompting.sql_compiler`. На неё возложены следующие обязанности:

- *Назначение алиасов.* Каждой задействованной таблице компилятор выдаёт короткий стабильный алиас вида `t1`, `t2`, ..., благодаря чему исключаются коллизии с резервированными именами Snowflake и улучшается читаемость генерации.
- *Безопасное цитирование имён.* В соответствии с case-sensitive семантикой Snowflake все имена столбцов оборачиваются в двойные кавычки. Это снимает целый класс ошибок регистра, особенно болезненных в запросах с camelCase-именами (`fullVisitorId`, `userPseudoId`).
- *Сборка `LATERAL FLATTEN`.* Для массивов внутри `VARIANT` автоматически формируется конструкция вида `LATERAL FLATTEN(input => t1."hits") h` с последующим обращением через `h.value:"event_name"::STRING`. На практике этот синтаксис тяжело даётся LLM-моделям, тогда как кодогенератор воспроизводит его без сбоев.
- *Сборка многоступенчатых CTE.* Если план описывает несколько именованных CTE с зависимостями друг от друга, компилятор разрешает порядок их объявления и собирает запрос вида `WITH cte1 AS (...), cte2 AS (...) SELECT ...`.
- *Постобработка партиций.* На завершающем шаге сканируется готовый SQL — в нём ищутся ссылки на представительские шарды партиционированной таблицы (например, `GA_SESSIONS_20170801`); при их наличии компилятор подставляет вместо такой ссылки UNION ALL CTE по нужному интервалу дат. Без этого шага запросы к GA360 (366 шардов) технически генерируются, но возвращают данные лишь за один день из всего интервала.

Эффективность подобного разделения подтверждается в исследовании абляции (Глава 7): отключение компилятора и переход к прямой генерации SQL моделью снижает точность на 36 процентных пунктов.

## 5.3. Best-of-N с диверсификацией стратегий

Шанс выйти на корректный ответ повышается параллельной генерацией нескольких независимых кандидатов плана. Для каждого пользовательского запроса агент создаёт $N=8$ планов одновременно, причём каждому кандидату назначается своя промпт-стратегия из ротации:

| Стратегия | На что делается акцент в промпте |
|:----------|:---------------------------------|
| `default` | Универсальная инструкция без специальных приоритетов |
| `join_first` | Сначала идентифицировать связи между таблицами |
| `metric_first` | Сначала выявить искомую числовую метрику и агрегацию |
| `time_first` | Приоритет временным измерениям и фильтрам по дате |
| `flatten_first` | Приоритет работе с `VARIANT`-полями через `LATERAL FLATTEN` |
| `cte_first` | Поощряется построение многоступенчатых CTE-конвейеров |
| `geo_first` | Приоритет геопространственным функциям (`ST_WITHIN`, `ST_DISTANCE` и т. п.) |
| `default` (второй экземпляр) | Дополнительный универсальный кандидат |

Каждый промпт смотрит на задачу с особой стороны и подталкивает модель к разному ходу рассуждения. Так, в `join_first` модель буквально начинает с фразы «определи, какие соединения потребуются для ответа», а в `metric_first` — с вопроса «что является целевой числовой величиной».

Каждому из восьми кандидатов разрешено компилироваться и исправляться независимо. Финальный выбор делает многосигнальный селектор — он вычисляет балл по формуле:

$$
\mathrm{score}(c) = w_1 \cdot \mathbf{1}[\mathrm{exec\_success}] + w_2 \cdot \mathrm{shape\_alignment}(c) - w_3 \cdot \mathrm{repair\_count}(c) + w_4 \cdot \mathrm{verifier\_prob}(c)
$$

где:

- $\mathbf{1}[\mathrm{exec\_success}]$ — индикатор того, что SQL-кандидат выполнился без ошибок;
- $\mathrm{shape\_alignment}$ — оценка соответствия формы результата ожидаемой (число строк, число столбцов, согласованность типов);
- $\mathrm{repair\_count}$ — штраф за количество итераций исправлений, понадобившихся данному кандидату;
- $\mathrm{verifier\_prob}$ — вероятностная оценка от верификатора, выполненного отдельной LLM-классификацией.

Если первый же кандидат прошёл выполнение без исправлений, он, как правило, получает максимальный балл и принимается без полного перебора.

## 5.4. Цикл самокоррекции (Repair Loop)

Каждый сгенерированный кандидат отправляется в Snowflake на исполнение. Цикл самокоррекции реализован в модуле `rag_snow_agent.agent.refiner` и работает в такой последовательности: «EXPLAIN → выполнить → классифицировать ошибку → отправить специализированный repair-промпт».

1. **Сначала EXPLAIN.** Прежде чем тратить ресурсы на полное исполнение, запрос отправляется на план-предпросмотр. Этот шаг отлавливает большинство синтаксических и семантических ошибок (несуществующие столбцы, несоответствие типов, проблемы с идентификаторами) без обращения к данным.
2. **Затем выполнение.** При успешном EXPLAIN запрос выполняется уже на боевых данных, и в систему возвращается набор результатов вместе с метаинформацией (число строк, столбцов, время выполнения).
3. **Классификация ошибок.** Если что-то пошло не так, текст ошибки Snowflake пропускается через `error_classifier`, который относит её к одной из категорий: `INVALID_IDENTIFIER`, `OBJECT_NOT_FOUND`, `AGGREGATION_ERROR`, `RESULT_MISMATCH`, `EMPTY_RESULT`, `NOT_AUTHORIZED`, `OTHER`.
4. **Адресный repair-промпт.** Под каждую категорию используется свой шаблон с дополняющей информацией:
   - на `INVALID_IDENTIFIER` запускается зонд `probe_column_exists` для проверки существования упомянутого столбца, а в промпт встраивается ближайший по написанию аналог из `SchemaSlice`;
   - на `OBJECT_NOT_FOUND` система достаёт из `SchemaSlice` список таблиц с похожими именами;
   - на `AGGREGATION_ERROR` подкладывается компактная справка о правилах `GROUP BY` в диалекте Snowflake;
   - на `RESULT_MISMATCH` в промпт включается сопоставление формы фактической и ожидаемой выдачи.
5. **Страховка от зацикливания.** Когда одна и та же категория ошибки повторяется три раза подряд, цикл останавливается с пометкой `error_type_threshold_exceeded`, чтобы не расходовать токены на бесперспективные правки.

Верхним пределом числа итераций для одного кандидата выбрано значение `max_repairs = 4`. Эмпирически после четвёртой итерации вероятность успешного исправления падает ниже 5 %, поэтому дальнейший расход бюджета токенов экономически нецелесообразен.

## 5.5. Обработка специфических случаев

### 5.5.1. Партиционирование по дате

В промышленных хранилищах временные ряды обычно лежат в виде ежедневных таблиц вида `EVENTS_20210101`, `EVENTS_20210102` и далее по списку. У GA360 одна логическая сущность представлена 366 шардами, физически независимыми друг от друга. Если работать с таким разбиением «в лоб», возникают две беды:

1. Ретривер «закапывается» в дублирующие карточки и не возвращает действительно нужные столбцы;
2. LLM ставит в `FROM` имя единственной — произвольной — партиции, теряя данные за остальные даты.

Применённое в системе решение работает на двух уровнях:

- *На этапе индексации:* все шарды объединяются в одну запись `TableCard` с указанием границ дат; столбцы сводятся в объединение по всем шардам, а имя таблицы берётся от последнего существующего шарда.
- *На этапе постобработки SQL:* собранный компилятором запрос проходит сканирование на ссылки к партиционированной таблице. Если в запросе обнаружен фильтр по дате — например, `"date" BETWEEN '20170701' AND '20170731'`, — компилятор автоматически подменяет ссылку на UNION ALL CTE, перебирающую нужный диапазон. При диапазонах сверх 40 дней (вроде условия `LIKE '2017%'`, охватывающего весь год) переписывание не выполняется, чтобы не уронить планировщик Snowflake по таймауту.

### 5.5.2. Геопространственные функции

Запросы с пространственной семантикой (`ST_WITHIN`, `ST_DISTANCE`, `ST_CONTAINS`) образуют отдельную сложность для LLM: модель путает порядок аргументов (lat/lon vs lon/lat), смешивает единицы измерения (метры с милями), а также часто забывает обернуть `VARCHAR`-геометрии вызовом `TO_GEOGRAPHY()`. В системе для таких случаев предусмотрены дополнительные элементы плана — `PlanGeoJoin` и `PlanGeoFilter`. Они передаются в компилятор как явные Pydantic-конструкции, если в выборке обнаруживаются геопространственные колонки. Параллельно стратегия `geo_first` подталкивает LLM к выбору этих конструкций вместо ручной арифметики над координатами.

### 5.5.3. Полуструктурированные данные `VARIANT`

`VARIANT` — это нативный тип Snowflake для полуструктурированных JSON-объектов. Доступ к вложенным полям различается принципиально в зависимости от того, что находится «под капотом» данной колонки: для массива требуется `FLATTEN`, для объекта работает оператор `:`. Ошибка в выборе синтаксиса гарантированно ломает компиляцию SQL. Чтобы исключить такие сбои, в системе классификация колонок выполняется ещё на этапе индексации — путём зондирования через `OBJECT_KEYS()` — и сохраняется в метаданных карточки. На этапе генерации промпта эта классификация передаётся LLM явным образом, что снимает необходимость угадывания.

# 6. Результаты бенчмарков

## 6.1. Методика и условия эксперимента

Все эксперименты проводятся на бенчмарке **Spider 2.0 — Snow** [4] — наборе из 547 запросов на естественном языке к 20 промышленным базам данных в облачном хранилище Snowflake (GA360, GA4, PATENTS, GITHUB_REPOS, NOAA_DATA, CMS_DATA и др.). Использовалось две выборки:

- **25-запросная подвыборка** — для базового сравнения с открытыми реализациями DSR-Lite, Spider-Agent (GPT-4o) [4] и ReFoRCE [8] на семействе из четырёх баз данных (GA4, GA360, PATENTS, PATENTS_GOOGLE);
- **100-запросная подвыборка** — первые 100 элементов файла `spider2-snow.jsonl`, охватывающие все 20 баз данных, использовалась для воспроизводимого сравнения с ReFoRCE на современной модели GPT-5.4-mini.

**Метрика точности — gold-match accuracy:** результат выполнения сгенерированного SQL-запроса на эталонной БД сравнивается с эталонным выводом, предоставленным авторами Spider 2.0. Совпадение определяется по форме и содержимому таблицы результата.

**Дополнительные метрики:**

- **valid SQL** — доля синтаксически корректных запросов, выполнившихся без ошибок;
- **pass@k** — доля задач, для которых хотя бы один из $k$ кандидатов прошёл gold-match (применима к ReFoRCE с её механизмом голосования);
- **total tokens** — суммарное количество токенов, затраченных всеми вызовами LLM (входные + выходные);
- **cost per correct answer** — оценочная стоимость одного правильного ответа в долларах США при тарифах OpenAI на момент проведения эксперимента.

Во всех экспериментах сравниваемые системы получали одну и ту же выборку запросов и работали с тем же подключением к Snowflake; единственным варьируемым параметром оставались архитектура конкретного Text-to-SQL метода и используемая в нём модель LLM.

## 6.2. Сравнение с базовыми методами на 25-запросной подвыборке

Эксперимент Run 9 предложенной системы (далее — SnowRAG-Agent) сравнивался с тремя базовыми методами на одинаковой подвыборке из 25 запросов:

| Метрика | DSR-Lite | Spider+GPT-4o | ReFoRCE | **SnowRAG-Agent (Run 9)** |
|:--------|---------:|--------------:|--------:|--------------------------:|
| Модель | DeepSeek | GPT-4o | GPT-5-mini | GPT-5.4 |
| Кандидатов на запрос | 1 | 1 | 8 | 8 |
| Итераций исправлений | 20 | 15 | 3 | 4 |
| **Gold-match accuracy** | 0 % | 12 % | 36 % | **92 %** |
| Правильных ответов | 0 / 23 | ≈ 3 / 25 | 9 / 25 | **23 / 25** |
| Всего токенов | 4,21 М | 3,90 М | 7,50 М | 4,08 М |
| Токенов на правильный ответ | ∞ | ≈ 1 300 000 | 833 485 | **177 229** |

**Ключевые наблюдения:**

1. SnowRAG-Agent демонстрирует точность **92 %**, превосходя ближайший базовый метод (ReFoRCE — 36 %) более чем в 2,5 раза.
2. Расход токенов на правильный ответ составляет **177 тыс.** против 833 тыс. у ReFoRCE — выигрыш в эффективности в **4,7 раза**.
3. На сложных доменах со сложной структурой (GA360, PATENTS) DSR-Lite, использующий полную DDL в промпте, не получил ни одного правильного ответа, тогда как SnowRAG-Agent достигает 92 % и 100 % соответственно.

Контраст с DSR-Lite заслуживает отдельного внимания. Используемая в этой системе модель (DeepSeek) уступает современным аналогам по силе генерации, но решающим оказывается не модель, а архитектура: полная DDL базы GA360 с её сотнями таблиц элементарно не помещается в окно контекста, и потому анализ запроса оказывается невозможен ещё до того, как может проявить себя любой алгоритм рассуждения или цикл коррекции.

Spider-Agent на GPT-4o выходит на чуть более высокую отметку (12 %) — здесь сказывается то, что GPT-4o аккуратнее восстанавливает структуру таблиц по именам. Однако и этого «угадывания» недостаточно, чтобы система устойчиво работала на промышленных схемах данных.

ReFoRCE со своим агентным циклом голосования и многошаговой коррекции добивается 36 %, но за это расплачивается примерно двукратным расходом токенов относительно SnowRAG-Agent. Узкое место здесь архитектурное: в ReFoRCE отсутствует ретривер, способный отдать в LLM именно ту часть метаданных, которая нужна под текущий запрос.

Сочетание 87 % gold-match и 38 центов за один правильный ответ показывает, что предложенный подход состоятелен с точки зрения промышленной эксплуатации.

Падение точности с 92 % (Run 9, 25 запросов на полной версии GPT-5.4) до 87 % (Run 10, 100 запросов на GPT-5.4-mini) объясняется двумя совместно действующими факторами. Для исключения различий, связанных с моделью и набором задач, был проведён прямой эксперимент Run 12 при идентичных условиях с upstream ReFoRCE: модель `gpt-5.4-mini`, та же выборка из 100 запросов, тот же эталон gold-match. ReFoRCE запускалась с типичными для архитектуры параметрами: `num_votes=8`, `num_workers=4`, `max_iter=5`, `test_delay=4`.

| Метрика | **SnowRAG-Agent (Run 12)** | **ReFoRCE** | Соотношение |

| Pass@k | — | 29 / 100 = 29,0 % | — |

Принципиально, что обе системы здесь функционируют на одной и той же модели (`gpt-5.4-mini`) и обрабатывают идентичный набор из 100 запросов. Тем самым любые расхождения между ними оказываются следствием исключительно различий в архитектуре. Это исключает гипотетический контраргумент о том, что преимущество SnowRAG-Agent могло бы объясняться выбором более мощной LLM.

**Анализ пересечения множеств правильных ответов:**

| Множество | Размер | Комментарий |

| Только ReFoRCE | **0** | — |
| Оба ошиблись | 16 | общий «ядерный» провал — преимущественно геопространственные запросы |

Особенность этого пересечения заключается в том, что **все** 20 запросов, корректно решённых ReFoRCE, одновременно успешно решены и SnowRAG-Agent. Не нашлось ни одной задачи, где наше решение уступило бы ReFoRCE. С методологической точки зрения этот результат имеет дополнительный смысл: он показывает, что архитектурные изменения SnowRAG-Agent не вносят регрессии — выборочный векторный поиск не «откидывает» нужную информацию, ухудшая работу относительно режима полного контекста.

При сравнении даже с pass@k ReFoRCE (любой из 8 сгенерированных кандидатов) лишь две задачи — `sf_bq056` и `sf_bq073` — обнаруживаются в множестве ReFoRCE, но не входят в gold-match SnowRAG-Agent. В обоих случаях ReFoRCE действительно сгенерировала правильный SQL, но в финальном голосовании выбрала неверный кандидат. Эти два примера наглядно показывают слабость голосования как механизма отбора в ситуации, когда среди кандидатов есть правильный ответ.

## 6.5. Архитектурные различия и их вклад в результат

| Характеристика | DSR-Lite | ReFoRCE | **SnowRAG-Agent** |
|:---------------|:---------|:--------|:------------------|
| Подход | Двухфазное рассуждение | Самоисправление + голосование | RAG + детерминированный компилятор плана |
| Извлечение схемы | Полная DDL | Полная DDL (после schema linking) | **Векторный поиск (ChromaDB) + RRF** |
| Описания столбцов | Нет | Нет | **LLM-профилирование (GPT-5.4) на 100 строках реальных данных** |
| Компилятор SQL | LLM напрямую | LLM напрямую | **Детерминированный (Plan → SQL)** |
| `LATERAL FLATTEN` | LLM | LLM | **Компилятор + перечень полей VARIANT** |
| Обработка партиций | Каждая таблица отдельно | Каждая таблица отдельно | **Объединение (366 → 1)** + post-compile UNION ALL |
| Геопространственные функции | LLM | LLM | Расширение схемы соседями + примитивы плана |
| Выравнивание ошибок | Регенерация | Регенерация | **Классификация ошибок + EXPLAIN-then-execute** |

**Ключевые факторы, обеспечившие преимущество в точности:**

1. **Профилирование данных + сгенерированные LLM описания.** Описания столбцов содержат точные пути доступа к VARIANT-полям и подсказки по форматам данных. Это устранило целый класс галлюцинаций — выдуманных вложенных полей, неправильных форматов дат и неверных интерпретаций столбцов с числовыми идентификаторами.
2. **Детерминированный компилятор Plan → SQL.** Отделяет рассуждение (LLM строит план) от форматирования SQL (детерминированный компилятор). Устраняет ошибки кавычек, алиасов, синтаксиса `LATERAL FLATTEN` и порядка CTE.
3. **Объединение партиций.** 366 ежедневных таблиц GA360 сворачиваются в одну запись индекса; столбцы — общие для всех партиций. Это решило проблему «загрязнения» результатов поиска и одновременно обеспечило корректную семантику запросов с диапазоном дат.

**Ключевые факторы, обеспечившие преимущество в стоимости:**

1. **Слайс схемы вместо полной DDL.** Средняя длина промпта SnowRAG-Agent — 4,7 К токенов на запрос против 26,7 К у ReFoRCE (в 5,6 раза меньше).
2. **Меньше итераций.** Точность отдельного кандидата выше, что уменьшает потребность в дополнительных проходах исправлений.
3. **Раннее завершение генерации.** Первый успешный кандидат принимается без необходимости голосования по всем 8.

## 6.6. Выводы по результатам бенчмарков

1. **Гипотеза работы подтверждена.** Использование RAG-архитектуры обеспечивает одновременное улучшение качества (84–87 % gold-match vs 20 % у ReFoRCE) и существенное снижение расхода токенов (в 6,9 раз) при сопоставимых параметрах генерации.
2. **Преимущество в качестве является «строгим».** Все запросы, корректно решаемые ReFoRCE, также корректно решаются SnowRAG-Agent. Не зафиксировано ни одного случая регресса в результате применения векторного отбора метаданных — следовательно, ретривер не отсекает критически важной информации.
3. **Стоимость одного правильного ответа.** SnowRAG-Agent — \$0,11 за правильный ответ, ReFoRCE — \$2,03. Разница в 18 раз делает SnowRAG-Agent экономически приемлемым решением для масштабной промышленной эксплуатации, тогда как ReFoRCE остаётся преимущественно исследовательской системой.
4. **Зона невозможности — общая для обеих систем.** 16 запросов не решены ни одним методом; преимущественно это геопространственные запросы и задачи с очень сложной семантикой, требующие либо более мощной модели, либо специальных архитектурных расширений. Эти случаи определяют направление дальнейших исследований.

## 7.2. Группировка компонентов по уровню вклада

**Уровень А: компоненты, отключение которых даёт падение более 50 пп.**

- *Сгенерированные LLM описания на основе профилирования* — лидер по влиянию. В отсутствие текстовых описаний модель сваливается в галлюцинирование путей доступа к `VARIANT`-полям и форматов дат. Описания формируют связующее звено между естественноязычным запросом и фактической структурой данных. Особенно болезненно их отсутствие проявляется на доменах с многослойными вложенными типами (GA360, PATENTS), где без описаний система фактически работает «вслепую».
- *Сворачивание партиционных таблиц* — компонент, без которого работа на доменах с сотнями ежедневных шардов (как у GA360) становится физически невозможной: ретривер захлёбывается в дублирующих карточках и теряет существенные столбцы. На однопартиционных базах (PATENTS, NOAA_DATA) этот механизм просто не задействуется и не влияет на результат — однако в условиях временного шардирования он становится решающим.

**Уровень Б: компоненты с вкладом 30–50 пп.**

- *Детерминированный компилятор Plan → SQL* устраняет систематические ошибки форматирования — кавычки, алиасы, синтаксис `FLATTEN`. Его роль особенно заметна в режиме множественных кандидатов: в отсутствие компилятора каждый из 8 кандидатов имеет независимые синтаксические дефекты, общее число которых пропорционально числу попыток.
- *Обогащение полей `VARIANT`* — обязательный компонент для PATENTS, GA360 и любого другого домена с вложенными структурами. Без классификации структуры (массив или объект) и перечня известных подполей LLM вынуждена «угадывать», что приводит к стабильному сбою на нестандартных именах подполей.
- *Сборка `LATERAL FLATTEN` в компиляторе* — формально частный случай предыдущего пункта, но настолько критичный, что заслуживает обособленного измерения.

**Уровень В: компоненты с вкладом 10–30 пп.**

- *Best-of-N с диверсификацией стратегий* — повышает шанс того, что хотя бы один из кандидатов попадёт в верный ответ. Особенно полезен на задачах, допускающих неоднозначную интерпретацию.
- *Цикл `max_repairs`* — гасит ошибки исполнения. По нашим наблюдениям, около 80 % успешных исправлений укладываются в первые 1–2 итерации; начиная с третьей итерации шансы на успех быстро падают.
- *Расширение 1-hop соседями* — догоняет таблицы, потерянные первичным поиском, но необходимые для построения соединений; работает как «страховка» от пропуска вспомогательных таблиц.

**Уровень Г: компоненты с вкладом менее 10 пп.**

- *`trace_memory`, `semantic_cards`, `sample_records`* — каждый из них поодиночке даёт небольшой прирост, но в совокупности повышают устойчивость на «пограничных» формулировках. На текущей 25-запросной выборке их роль ограничена тем, что лишь немногие задачи попадают в зону их специализации.

## 7.3. Сравнение базовой LLM (без RAG) и полной системы

Конфигурация «без RAG», в которой полная DDL базы данных подаётся непосредственно в промпт LLM, выдаёт **36 % точности** — это, по сути, тот же уровень, что у ReFoRCE с её куда более сложной агентной архитектурой. Полученный результат подтверждает главную гипотезу работы: **на промышленных схемах уровня Spider 2.0 ключевую роль играет именно структурный отбор метаданных, а не количество вызовов LLM или мощность модели как таковой.**

Без RAG модель GPT-5.4 не масштабируется на базы вроде GA360 (12 столбцов вложенной структуры × 366 партиций × 12 запросов): полная DDL либо не вмещается в контекстное окно, либо влечёт деградацию качества из-за рассеивания внимания модели по нерелевантным фрагментам.

Дополнительно отметим, что разрыв между «RAG без профилирования» (24 %) и «полная DDL без RAG» (36 %) — всего 12 пп. Это значительно меньше, чем 92 % полной системы. Иными словами, использовать RAG без качественных описаний нецелесообразно, но и одна только полная DDL не заменяет совместной работы трио «RAG + описания + компилятор».

## 7.4. Стабильность результата

Каждая из конфигураций прогонялась трижды с фиксированным набором seed-значений. Стандартное отклонение точности между запусками не превышало ±2 пп; в таблице приведены медианные значения. Это означает, что зафиксированные различия между конфигурациями (особенно при $|\Delta| > 5$ пп) являются статистически значимыми.

# 8. Заключение

Настоящая работа представила законченное исследование задачи Text-to-SQL применительно к промышленным схемам данных и сформулировала архитектуру системы SnowRAG-Agent, опирающуюся на динамический RAG с гибридным векторным поиском. Все восемь задач, поставленных во введении, выполнены и подтверждены экспериментальными данными.

**Полученные результаты:**

1. Создана **векторная база знаний** из пяти специализированных коллекций — `schema_cards`, `semantic_cards`, `sample_records`, `trace_memory` и `snowflake_syntax`, — которые в совокупности покрывают значимые виды метаданных схемы. Принцип «один объект — одна запись» обеспечивает атомарность извлечения и точную фильтрацию по типу запрашиваемой информации.

2. Реализован **гибридный механизм поиска**, объединяющий плотный семантический проход (модель `text-embedding-3-large`) и лексический BM25-проход; результаты двух проходов сводятся через Reciprocal Rank Fusion. Такой механизм одинаково устойчиво работает как на естественноязычных формулировках запроса, так и на идентификатор-ориентированных.

3. Спроектирован **детерминированный компилятор Plan → SQL**, разводящий ответственность за высокоуровневое рассуждение (остаётся за LLM) и за форматирование выходного SQL (берёт на себя компилятор). Реализованы характерные для Snowflake конструкции — `LATERAL FLATTEN`, обращение к `VARIANT`, многоступенчатые CTE, — что снимает с LLM целый пласт синтаксических ошибок.

4. Выстроен **цикл самокоррекции**, в котором ошибки Snowflake классифицируются по семи категориям, и под каждую из них применяется свой repair-промпт. На практике типичные сбои исполнения устраняются за 1–2 итерации.

5. На бенчмарке Spider 2.0 — Snow зафиксированы следующие количественные показатели:
   - на 25-запросной подвыборке — **92 % gold-match accuracy** против 36 % у ReFoRCE и 0 % у DSR-Lite;
   - на 100-запросной подвыборке (модель `gpt-5.4-mini`) — **87 % gold-match accuracy**;
   - в прямом сопоставлении на одинаковых 100 запросах при одинаковой модели SnowRAG-Agent опережает upstream-реализацию ReFoRCE **в 4,2 раза по точности**;
   - суммарный расход токенов сокращён **в 6,9 раза**, а стоимость одного правильного ответа — **в 18 раз**.

6. Проведено **исследование абляции** 12 конфигураций. Оно определило три компонента наибольшего вклада — описания, сгенерированные LLM по результатам профилирования; сворачивание партиционных таблиц на этапе индексации; детерминированный компилятор Plan → SQL — и подтвердило, что определяющим фактором качества выступает именно структурный отбор метаданных, а не количество итераций или мощность модели как таковой.

**Научная новизна работы.** Ключевое нововведение состоит в архитектуре сущностно-ориентированного RAG, при которой документ индекса представляет собой отдельный элемент метаданных (таблицу, столбец, связь, семантический факт), а не текстовый фрагмент фиксированной длины. Введён обязательный шаг сворачивания партиционных таблиц на этапе формирования индекса — он отсекает «шум» от временных шардов. Разработан кодогенератор Plan → SQL, ориентированный на специфику Snowflake (`LATERAL FLATTEN`, доступ к `VARIANT`, конвейеры CTE).

**Практическая значимость.** Получившийся программный комплекс, развёрнутый в публичной облачной среде, демонстрирует показатели, пригодные к промышленной эксплуатации: 87 % gold-match accuracy при стоимости порядка \$0,11 за правильный ответ. Эта величина в 18 раз ниже, чем у эталонной реализации ReFoRCE при сопоставлении на тех же данных и той же модели. Решение применимо в качестве встраиваемого «помощника аналитика» — компонента BI-платформ и корпоративных дашбордов.

**Ограничения и направления дальнейших исследований.** В финальном бенчмарке остаются нерешёнными 16 запросов из 100 — преимущественно это геопространственные сценарии и задачи с многошаговой статистической логикой. Их разрешение, по-видимому, потребует либо подключения более мощной LLM, либо введения специализированных подсистем — в частности, отдельного агента для геопространственного анализа. Перспективными представляются также эксперименты по переносу подхода на другие облачные платформы (BigQuery, Redshift) с оценкой устойчивости к различиям SQL-диалектов; автоматизация наполнения `trace_memory` за счёт накапливаемых пользовательских сессий, при которой система самостоятельно улучшает качество ответов в продолжительной эксплуатации; применение более продвинутых моделей эмбеддингов и доменно-специализированных моделей (Snowflake Cortex Embed, fine-tuned-варианты) для дальнейшего сокращения числа ложных совпадений на этапе ретривала.

# 10. Приложение

## 10.1. Архитектура программного комплекса

Кодовая база SnowRAG-Agent написана на Python версии 3.11 с менеджером зависимостей `uv` и поделена на четыре подсистемы.

**Ядро агента — каталог `rag_snow_agent/src/rag_snow_agent/`.** Здесь сосредоточены реализация векторного хранилища, ретривера, компилятора Plan → SQL и цикла самокоррекции. Внешние зависимости: `chromadb` (векторный индекс), `openai` (вызовы LLM и эмбеддингов), `snowflake-connector-python` (подключение к хранилищу), `pydantic` (валидация структуры плана запроса).

**Backend-сервис — каталог `rag_snow_agent/backend/`.** Сервис построен на FastAPI и публикует REST API со следующими эндпоинтами:

| Эндпоинт | Метод | Назначение |
|:---------|:-----:|:-----------|
| `/api/chat` | POST | Передача нового сообщения и запуск генерации SQL по вопросу |
| `/api/sessions` | GET | Получение истории сессий пользователя |
| `/api/sessions/{id}` | DELETE | Удаление выбранной сессии |
| `/api/config` | GET / POST | Чтение и обновление настроек агента |
| `/api/databases` | GET | Список баз данных, доступных для запроса |
| `/api/health` | GET | Healthcheck сервиса |

История диалогов хранится в SQLite-базе по пути `rag_snow_agent/data/sessions.db`. Это позволяет сохранять переписку между запусками сервиса и анализировать траекторию решения сложных задач постфактум.

**Frontend — каталог `rag_snow_agent/frontend/`.** Клиентская часть реализована на React и TypeScript с использованием сборщика Vite и UI-компонентов TailwindCSS. Состав интерфейса:

- основная панель чата с Markdown-разметкой и подсветкой SQL-синтаксиса;
- панель настроек, дающая возможность сменить LLM-модель, изменить значения параметров Best-of-N и max_repairs, а также включать или отключать отдельные RAG-компоненты для интерактивной отладки;
- панель истории сессий с переходом к предыдущим разговорам;
- виджет визуализации `SchemaSlice` — отображает таблицы и столбцы, которые ретривер фактически отобрал для текущего запроса, благодаря чему работа системы остаётся прозрачной для пользователя.

**Скрипты офлайн-обработки — каталог `rag_snow_agent/scripts/`.** Среди них: `profile_data.py` (статистическое профилирование таблиц на 100-строчных выборках), `enrich_descriptions.py` (генерация описаний моделью GPT-5.4 и загрузка в `ChromaDB`), `build_index.py` (построение индекса с нуля), `run_benchmark.py` (запуск бенчмарка Spider 2.0 в воспроизводимом режиме).

## 10.2. Пример пользовательского сценария

Типичный путь использования системы выглядит следующим образом.

1. Пользователь заходит на веб-страницу приложения и в выпадающем списке выбирает целевую БД Snowflake — например, `GA360`.
2. В поле чата вводится вопрос на естественном языке: «Какие 10 страниц чаще всего открывали пользователи из США в июле 2017 года?».
3. Backend получает запрос и запускает обработку:
   - обращается к ретриверу за релевантными метаданными для базы `GA360` и текста вопроса;
   - получает на выходе `SchemaSlice` размером ≈3 000 токенов с описанием представительской таблицы `GA_SESSIONS_*`, ключевых столбцов (`hits`, `geoNetwork`, `date`, `fullVisitorId`) и связанных семантических фактов;
   - параллельно отправляет восемь промптов с разными стратегиями в LLM;
   - получает восемь планов запроса и пропускает их через детерминированный компилятор;
   - проверяет каждый кандидат через `EXPLAIN`, а в случае ошибки — запускает соответствующий repair-цикл.
4. Через 30–60 секунд в чате появляется ответ, состоящий из:
   - сгенерированного SQL-запроса с подсветкой синтаксиса;
   - таблицы с результатами исполнения (10 строк: URL страницы и число просмотров);
   - служебной информации — количество затраченных токенов, число итераций исправления, выбранная стратегия;
   - кнопки «Объяснить», по нажатию которой система комментирует логику построенного SQL на естественном языке.
5. Если пользователь задаёт уточняющий вопрос («а теперь по дням недели»), система задействует контекст предыдущего успешного решения — через коллекцию `trace_memory` — для генерации нового SQL без повторного «знакомства» с предметной областью.

## 10.3. Развёртывание в облачной среде

Программный комплекс развёрнут в публичной облачной среде с разделёнными Docker-образами для backend- и frontend-частей. Слой персистентности — ChromaDB и SQLite-база сессий — смонтирован как persistent volume, что обеспечивает сохранность накопленных данных и истории сессий при перезапусках сервисов. Подключение к Snowflake производится через сервисный аккаунт с правами «только на чтение», в соответствии с принципом наименьших привилегий.

## 10.4. Воспроизводимость экспериментов

Любой из бенчмарков, описанных в работе, может быть воспроизведён по шагам:

1. Клонировать репозиторий и установить зависимости командой `uv sync`.
2. Скопировать `.env.example` в `.env` и заполнить переменные `OPENAI_API_KEY`, а также учётные данные Snowflake.
3. Построить индекс: `python -m rag_snow_agent.scripts.build_index`.
4. Запустить бенчмарк, например:

   ```bash
   python -m rag_snow_agent.eval.experiment_runner \
     --split_jsonl Spider2/spider2-snow/spider2-snow.jsonl \
     --experiment my_run \
     --limit 100 \
     --model gpt-5.4-mini \
     --best_of_n 8 \
     --max_repairs 4 \
     --gold_dir Spider2/spider2-snow/evaluation_suite/gold/
   ```

5. Получить готовый отчёт в каталоге `rag_snow_agent/reports/experiments/my_run/`.

Все артефакты экспериментов — результаты по экземплярам, логи, манифесты — фиксируются в репозитории: агрегированные отчёты лежат в `docs/benchmarks/`, а детальные данные по каждому запуску — в `rag_snow_agent/reports/experiments/`. Такая организация обеспечивает прозрачность и независимую проверяемость заявленных в работе результатов.
