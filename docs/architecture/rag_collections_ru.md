# Описание коллекций векторной базы данных RAG-системы

## Общая характеристика хранилища

В качестве векторной базы данных используется ChromaDB — встраиваемое хранилище с поддержкой персистентного хранения на диске. Каталог хранения: `rag_snow_agent/.chroma/`. Для вычисления векторных представлений (эмбеддингов) используется модель `text-embedding-3-large` компании OpenAI, генерирующая вектора размерностью 3072. В качестве метрики сходства применяется косинусное расстояние.

Хранилище организовано в пять тематических коллекций, каждая из которых выполняет определённую функцию в процессе генерации SQL-запросов.

---

## Коллекция 1: `schema_cards` (622 элемента)

**Назначение.** Основная база знаний системы, содержащая структурированные описания объектов схемы данных — таблиц, столбцов и связей между таблицами. Используется на этапе контекстного извлечения для формирования компактного представления схемы (SchemaSlice), которое включается в промпт языковой модели.

**Типы хранимых записей:**

### TableCard — карточка таблицы
Для каждой таблицы базы данных создаётся одна карточка. Партиционированные таблицы (например, ежедневные таблицы Google Analytics формата `GA_SESSIONS_YYYYMMDD`, насчитывающие 366 отдельных таблиц) объединяются в одну репрезентативную запись. В качестве имени используется реально существующая в Snowflake таблица последней партиции, а в описание включается информация о диапазоне дат и способе фильтрации.

Текстовое представление (документ) включает имя таблицы, описание на естественном языке и список столбцов. Описание генерируется моделью GPT-5.4 на основе профилирования 100 строк реальных данных, что обеспечивает семантически осмысленный поиск: запрос пользователя о «выручке» будет сопоставлен с таблицей, в описании которой упоминаются транзакционные данные.

Метаданные: идентификатор базы данных (`db_id`), квалифицированное имя таблицы, описание на естественном языке, оценка количества токенов.

### ColumnCard — карточка столбца
Для каждого столбца создаётся отдельная запись, включая столбцы вложенных полей типа VARIANT. Описания столбцов генерируются на основе статистического профиля данных (доля пустых значений, диапазон значений, количество уникальных значений, структура вложенных объектов) и содержат указания по корректному построению SQL-запросов.

Для столбцов типа VARIANT описание включает классификацию структуры — ARRAY (требуется оператор `LATERAL FLATTEN`) или OBJECT (используется доступ через двоеточие), а также перечень известных вложенных полей с указанием их типов данных.

Вложенные поля VARIANT-столбцов (например, `"totals":pageviews`) хранятся с типом данных `VARIANT_FIELD` и содержат в метаданных признак источника обнаружения — через прямой вызов `OBJECT_KEYS()` (объектная структура) или через `LATERAL FLATTEN + OBJECT_KEYS()` (элемент массива). Этот признак определяет классификацию родительского столбца при формировании промпта.

### JoinCard — карточка связи
Для каждой обнаруженной связи между таблицами создаётся запись, содержащая левую и правую таблицы, столбцы соединения, уровень уверенности (1.0 для внешних ключей, 0.7 для эвристических совпадений) и источник обнаружения.

## Коллекция 2: `semantic_cards` (5 762 элемента)

**Назначение.** Хранилище семантических фактов, выведенных из метаданных схемы с помощью детерминированных эвристик. Используется для обогащения контекста промпта дополнительными подсказками о структуре и семантике данных.

**Типы семантических фактов:**

- **primary_time_column** — столбцы с типами DATE, TIMESTAMP и их разновидностями. Позволяет системе автоматически определять временные измерения.
- **date_format_pattern** — столбцы с датоподобными именами и числовым или текстовым типом. Классифицируются как «YYYYMMDD целое число» (для числовых столбцов) или «YYYYMMDD строка» (для текстовых). Эта информация критична для корректной генерации условий фильтрации по дате.
- **metric_candidate** — числовые столбцы, имена которых указывают на метрическое содержание (revenue, count, price, total и т.д.).
- **dimension_candidate** — текстовые столбцы с именами, характерными для аналитических измерений (source, country, category, status и т.д.).
- **nested_container_column** — столбцы типов VARIANT, OBJECT и ARRAY с указанием классификации структуры и известных вложенных полей.
- **identifier_column** — столбцы, соответствующие шаблонам идентификаторов (`*_ID`, `*_KEY`, `ID`). Используются для защиты от удаления при оптимизации бюджета токенов.

Каждый факт сопровождается уровнем уверенности (от 0.0 до 1.0) и указанием источника (метаданные, эвристики, зонды).

---

## Коллекция 3: `sample_records` (10 элементов)

**Назначение.** Хранение образцов данных из таблиц для включения в контекст промпта. Каждый элемент содержит 2–5 строк из одной таблицы, отформатированных в виде компактного JSON.

Образцы данных позволяют языковой модели «увидеть» реальные значения столбцов, понять формат дат, структуру вложенных VARIANT-объектов и типичные диапазоны значений. Это особенно важно для таблиц со сложной структурой, таких как Google Analytics, где столбец `hits` содержит массив вложенных объектов с десятками полей.

---

## Коллекция 4: `trace_memory` (5 элементов)

**Назначение.** Хранение успешных решений для контекстного обучения на примерах (few-shot learning). При успешном решении задачи система сохраняет пару «вопрос — план решения» для последующего использования в качестве примера при решении семантически близких задач.

Документ содержит краткое изложение вопроса и плана решения. Метаданные включают идентификатор базы данных, идентификатор экземпляра задачи и список использованных таблиц. Поиск выполняется по семантической близости к текущему вопросу с фильтрацией по базе данных.

Данный механизм реализует принцип «обучения на собственном опыте»: система накапливает библиотеку успешных решений и использует их для повышения качества генерации на аналогичных задачах.

---

## Коллекция 5: `snowflake_syntax` (55 элементов)

**Назначение.** Справочник синтаксиса Snowflake SQL, используемый на этапе исправления ошибок в сгенерированных запросах. Содержит фрагменты документации по синтаксису различных конструкций: соединения таблиц (JOIN), оператор `LATERAL FLATTEN`, оконные функции, операции с типами данных и другие.

При возникновении ошибки компиляции или выполнения SQL-запроса система формирует поисковый запрос из текста ошибки и фрагмента SQL, извлекает релевантные справочные фрагменты и включает их в промпт для исправления. Это позволяет модели использовать точную справочную информацию о синтаксисе Snowflake вместо генерации исправлений «по памяти».

## Процесс наполнения коллекций

### Индексирование схемы (онлайн)
Выполняется командой `build_index.py` при подключении к Snowflake. Извлекает таблицы, столбцы, типы данных и связи из `INFORMATION_SCHEMA`. Для VARIANT-столбцов выполняет зондирование структуры через `OBJECT_KEYS()` и `LATERAL FLATTEN`. Партиционированные таблицы объединяются в одного представителя.

### Профилирование данных (офлайн)
Выполняется скриптом `profile_data.py`. Для каждой таблицы извлекается 100 строк данных, вычисляется статистический профиль каждого столбца, затем модель GPT-5.4 генерирует текстовые описания таблиц и столбцов на естественном языке. Описания сохраняются в файл `table_column_descriptions.json` и загружаются в коллекцию `schema_cards` через скрипт обогащения `enrich_descriptions.py`.

### Семантические факты (автоматически)
Генерируются детерминированными эвристиками модуля `infer_from_metadata.py` на основе типов данных, имён столбцов и результатов зондирования VARIANT-структур.

---

## Использование коллекций в процессе генерации SQL

На каждый пользовательский запрос система обращается к коллекциям в следующем порядке:

1. **schema_cards** — гибридный поиск (семантический + лексический + RRF-слияние) для извлечения релевантных таблиц и столбцов. Результат: SchemaSlice с бюджетом до 10 000 токенов.

2. **semantic_cards** — извлечение семантических фактов для обогащения контекста (форматы дат, кандидаты на метрики, классификация VARIANT-структур).

3. **sample_records** — извлечение образцов данных для релевантных таблиц.

4. **trace_memory** — поиск семантически близких успешных решений для формирования контекста few-shot.

5. **snowflake_syntax** — обращение только при возникновении ошибок на этапе исправления SQL-запросов.

---

## Процесс извлечения информации (Retrieval Pipeline)

### Стратегия разбиения на фрагменты (Chunking)

В отличие от классических RAG-систем, работающих с произвольными текстовыми документами, данная система оперирует структурированными метаданными схемы базы данных. Вместо разбиения документа на фрагменты фиксированного размера применяется стратегия **«один объект — один фрагмент»** (entity-level chunking):

- **TableCard** — один фрагмент на таблицу. Документ включает квалифицированное имя (`DB.SCHEMA.TABLE`), описание на естественном языке, список столбцов, временные столбцы и ключи соединения. Типичный размер: 60–300 токенов.
- **ColumnCard** — один фрагмент на столбец. Документ содержит квалифицированное имя столбца, тип данных и описание. Для VARIANT-столбцов описание включает способ доступа к вложенным полям и их перечень. Типичный размер: 20–400 токенов (зависит от сложности описания).
- **JoinCard** — один фрагмент на связь между таблицами. Документ описывает левую и правую стороны связи с указанием уровня уверенности. Типичный размер: 20–40 токенов.

Такая стратегия обеспечивает точную атомарность извлечения: система может извлечь конкретный столбец или конкретную таблицу, не загружая избыточный контекст.

Для партиционированных таблиц (GA360, GA4) применяется **предварительное объединение** (partition collapsing): 366 ежедневных таблиц GA360 сводятся к одной репрезентативной карточке, что исключает дублирование в результатах поиска и экономит бюджет контекста.

### Этап 1: Плотный семантический поиск (Dense Retrieval)

На вход подаётся вопрос пользователя на естественном языке. Система формирует векторное представление (эмбеддинг) запроса с помощью модели `text-embedding-3-large` и выполняет поиск ближайших соседей в пространстве ChromaDB по косинусному расстоянию.

Поиск выполняется раздельно для двух типов объектов:
- **Таблицы** (`object_type=table`): извлекается до `top_k_tables × 2` кандидатов (избыточная выборка для последующего реранкинга).
- **Столбцы** (`object_type=column`): извлекается до `top_k_columns × 2` кандидатов.

Фильтрация по `db_id` выполняется на уровне ChromaDB через параметр `where`, что обеспечивает изоляцию данных разных баз.

Результат: упорядоченный список идентификаторов объектов (dense_ranked), отсортированный по убыванию семантической близости.

### Этап 2: Лексический поиск (Lexical Retrieval)

Параллельно выполняется лексическое сопоставление. Запрос пользователя и квалифицированное имя каждого объекта токенизируются путём разбиения по разделителям (`_`, `.`, пробел) и границам CamelCase. Все токены приводятся к нижнему регистру.

Для каждого объекта-кандидата вычисляется **пересечение множеств токенов** (token overlap) между запросом и именем объекта. Объекты упорядочиваются по убыванию количества совпавших токенов.

Пример: запрос *«total transaction revenue by traffic source»* токенизируется в `{total, transaction, revenue, by, traffic, source}`. Столбец `trafficSource.source` токенизируется в `{traffic, source, source}`. Пересечение: `{traffic, source}` — 2 совпадения, что обеспечивает высокий лексический ранг.

Результат: упорядоченный список идентификаторов (lexical_ranked), отсортированный по количеству совпавших токенов.

### Этап 3: Слияние результатов методом RRF (Reciprocal Rank Fusion)

Два ранжированных списка (семантический и лексический) объединяются по формуле Reciprocal Rank Fusion:

$$\text{RRF\_score}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)}$$

где:
- $R$ — множество ранжированных списков (в данном случае два: dense и lexical),
- $\text{rank}_r(d)$ — позиция документа $d$ в списке $r$ (начиная с 1),
- $k$ — параметр сглаживания (по умолчанию $k = 60$).

Параметр $k$ контролирует баланс между списками: при $k = 60$ объекты с высоким рангом в обоих списках получают значительное преимущество, но объект, присутствующий только в одном списке, не отбрасывается.

Результат: единый список объектов, упорядоченный по убыванию RRF-оценки. Каждый элемент сохраняет информацию о позиции в обоих исходных списках (`dense_rank`, `lexical_rank`), объединённой позиции (`fused_rank`) и RRF-оценке (`rrf_score`).

### Этап 4: Формирование SchemaSlice

Извлечённые таблицы и столбцы группируются в структуру `SchemaSlice`:
1. Для каждой извлечённой таблицы создаётся `TableSlice` с описанием и комментарием.
2. Извлечённые столбцы распределяются по соответствующим таблицам.
3. Если для таблицы не извлечено ни одного столбца, выполняется запрос к ChromaDB для получения полного списка столбцов этой таблицы (fallback-механизм).
4. Столбцы типа `VARIANT_FIELD` (вложенные поля) исключаются из списка — их информация переносится в поле `variant_fields` родительского VARIANT-столбца.

### Этап 5: Обогащение VARIANT-полей

Для каждой таблицы в SchemaSlice выполняется дополнительный запрос к ChromaDB для извлечения записей типа `VARIANT_FIELD`, принадлежащих данной таблице. Найденные вложенные поля группируются по родительскому столбцу и присоединяются к соответствующему `ColumnSlice` в виде списка `variant_fields`.

На основе комментария VARIANT_FIELD записи определяется классификация родительского столбца:
- Если вложенные поля обнаружены через `LATERAL FLATTEN + OBJECT_KEYS` (признак «array element» в комментарии) — столбец классифицируется как **ARRAY** (требуется оператор LATERAL FLATTEN).
- Если поля обнаружены через прямой `OBJECT_KEYS` — столбец классифицируется как **OBJECT** (используется доступ через двоеточие).

### Этап 6: Расширение связности (Connectivity Expansion)

Если извлечённые таблицы не связаны между собой через ключи соединения, система предпринимает поиск «мостовой» таблицы:

1. **Через граф связей (JoinGraph)**: из коллекции `schema_cards` извлекаются JoinCard-записи для данной базы данных. Строится граф связей, выполняется поиск кратчайшего пути (BFS) между несвязанными таблицами с учётом уровня уверенности связей. Добавляются промежуточные таблицы-мосты.

2. **Эвристический метод (fallback)**: если JoinCard-записи отсутствуют, выполняется поиск таблицы, столбцы которой (с именами типа `*_ID`, `*_KEY`) пересекаются со столбцами двух или более извлечённых таблиц.

### Этап 7: Оптимизация бюджета токенов (Budget Trimming)

SchemaSlice подвергается итеративному сокращению для соблюдения бюджета (по умолчанию 10 000 токенов):

1. **Классификация столбцов**: каждый столбец помечается как `is_join_key` (содержит `_ID`, `_KEY`, `ID` в имени) или `is_time_column` (содержит `DATE`, `TIME`, `TIMESTAMP` в имени или типе). Также определяются `variant_kind` и `date_format`.

2. **Защита критических столбцов**: столбцы с пометкой `is_join_key` или `is_time_column` получают защиту от удаления.

3. **Итеративное удаление**: на каждой итерации удаляется незащищённый столбец с наихудшим рангом (наибольшим `fused_rank`). При равенстве рангов предпочтение отдаётся столбцам из таблиц с худшим рангом.

4. **Удаление пустых таблиц**: если все столбцы таблицы удалены, удаляется сама таблица.

5. **Удаление целых таблиц**: если после удаления отдельных столбцов бюджет всё ещё превышен, удаляются таблицы с наихудшим рангом целиком.

### Этап 8: Форматирование для промпта

Финальный SchemaSlice форматируется в текстовое представление для включения в промпт LLM. Формат:

```
-- Database: GA360
TABLE GA360.GOOGLE_ANALYTICS_SAMPLE.GA_SESSIONS_20170630  -- описание таблицы
  hits VARIANT ARRAY — use LATERAL FLATTEN(...) [fields: page.pagePath, product.v2ProductName, ...]
  totals VARIANT OBJECT — access with t."totals":"field"::TYPE [fields: hits, pageviews, ...]
  date TEXT — date as string (YYYYMMDD), compare with >= '20170201' -- описание столбца
  fullVisitorId TEXT -- уникальный идентификатор посетителя
```

Каждый столбец сопровождается:
- Аннотацией типа данных с указанием VARIANT-классификации (ARRAY/OBJECT) и известных вложенных полей.
- Указанием формата даты и способа сравнения (для временных столбцов).
- Комментарием с описанием на естественном языке (из профилирования данных).
